## 第一个工作包：P2-WP01 最小范围

业务问题：材料写了人员/区域，但模型不能凭描述猜测其资质或区域状态。先在本地合成数据上执行有身份边界的查询，再为模型选择工具建立可信基础。

建议两个工具：`query_worker_qualification`、`query_area_status`。参数只接受明确的业务对象ID和本次核验所需条件；tenant/user由服务入口的可信上下文提供，不允许模型改写。对象ID可由合成申请/测试输入提供，跨租户或无权对象不能因“知道ID”而读到数据。

数据是标记SYNTHETIC的版本化本地JSON记录；函数实际查询/过滤记录，不硬编码各案例答案。结果包含工具标识、对象引用、来源版本、查询时间、数据有效期、事实值或明确的unknown/error。人员资质缺失/过期与查询超时分别表达；不把失败当作资质不合格，不给作业批准结论。时间由可注入时钟提供，测试不依赖当天日期碰巧通过。

首包采用代码决定的固定只读查询顺序，暂不让模型规划查询。通过当前CLI或单独事实核验入口演示，复用task/run/correlation关联，查询结果放独立证据结构，不把模型/工具输入直接写入生命周期字段。保留P1四字段合同兼容，不需要重构已验证恢复模块。

建议新增 `src/anlan/tools/` 存放这两个工具及共享结果合同；`examples/synthetic/`保存数据；测试在`tests/`。如果一个小模块已足够，不为每个工具创建一套Service/Repository抽象。具体接入点经冷启动读代码后确定，在本阶段工作包计划中说明。

验收演示：合成申请引用某人员/区域 → 执行查询 → 显示来源/时效事实或未知 → 等待安全管理人员复核。注入一次超时与一次跨租户请求，验证可读错误/拒绝和状态不被越权改写。首包不消耗真实模型调用，无需新的密钥信息。

### 2026-09-20 冷启动后的接入方案（用户已确认，WP01已通过）

核对依据见[cold-start](cold-start.md)。推荐独立 `check-facts` CLI入口，通过 `WorkflowService.get(identity, task_id)` 校验归属并读取当前材料快照，再按固定顺序执行两个查询。业务对象ID及所需资质类型从单独的合成引用输入提供，不从四字段自然语言中猜测；该输入禁止tenant/user或生命周期字段。

查询使用新的核验run_id，沿用task_id/correlation_id，并记录源材料revision/source_run_id，避免把新查询冒充为原材料分析。两个结果在独立证据结构中输出，写必要关联轨迹，不改变P1图状态、提交回执或checkpoint合同。查询有记录时报告版本与有效期；缺失/过期/不适用是明确事实可用性原因，参数错误/无权/超时/数据读取失败是查询错误；失败不等于资质不合格。时间与延迟可注入，授权在读取业务事实前执行，拒绝结果不泄漏其他租户记录。

当前CLI会为多数deepseek模式命令初始化模型分析器，因此新入口必须在模型初始化前分流，事实核验路径不加载模型配置、不构造模型客户端。沿用本地模拟Identity，仅证明入口与参数隔离，不冒称生产认证。

另一种接法是直接加Graph节点：能自动串联材料与事实，但会牵动已冻结状态/恢复合同；首包暂不选。独立入口的代价是先得到单独证据包，尚未自动合并为综合风险结论。后续WP02再接有界模型工具循环，本包不安装pgvector/Langfuse、不建多Agent或通用平台。

首包完成需通过acceptance中的正常/未知/错误/越权/超时场景与P1回归，并留下CLI演示、测试原始结果、架构/状态/能力矩阵/学习记录与工作包handoff。当前WP01验收已通过，证据见[交接](wp01-handoff.md)；后续按持续授权推进。
