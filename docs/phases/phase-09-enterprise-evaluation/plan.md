# P9 企业级评测强化计划

## 1. 目标与结论边界

本阶段把安澜现有的小规模合成评测，升级为能够支持企业试点决策的安全生产 Agent 评测体系。重点不是增加功能，而是回答四个问题：

1. Agent 在哪些业务条件下可靠，在哪些条件下必须转人工；
2. 每条风险判断是否得到当前事实和有效制度支持；
3. 系统改动是否改善效果，是否引入新的高严重错误；
4. Agent、工具或模型失败时，是否仍能保护租户、业务状态和原始告警链路。

阶段完成只能证明限定数据、版本和环境下的质量证据更可信，不等于生产安全认证、法定合规结论或真实企业规模验证。

## 2. 当前基线

现有工程已经具备版本化数据、确定性评分、开发/留出概念、有限真实模型实验、Judge 校准、单/多 Agent 与 Memory 对照、Badcase 回放、失败保留、token/延迟记录和阶段 Gate。

主要缺口是：

- 数据规模小，主要为开发者已见的合成案例；
- `quality-v1` 的留出集由 AI 构造，首次运行后已经暴露，不能继续称为真正未见测试集；
- 多处只检查结构、工具结果或引用存在，尚未逐条验证自由文本风险主张是否被证据支持；
- 尚无独立安全领域人员形成的正式金标和评分记录；
- 指标散落在多个脚本中，没有统一的风险等级、发布门禁和版本比较报告；
- 对照实验样本少、重复运行不足，不能推断泛化效果；
- 有追踪和人工反馈能力，但还没有形成影子运行质量监控和人工协作效果评测。

现有数据与报告不删除、不改写；它们作为历史回归和失败证据继续保留。

## 3. 评测原则

### 3.1 先定义风险，再定义数据和分数

每个案例先标明业务目的、风险等级、必须发现的风险、允许保留的未知、必须追问的问题、必须引用的事实或制度，以及禁止生成的结论或动作。数据集只是这些标准的载体。

### 3.2 结果和过程分别评分

最终建议正确不能抵消错误的工具调用、跨租户访问、过期制度、旧 revision、遗漏未知项或证据不匹配。评测同时保存并检查模型输入输出、工具调用、检索结果、状态版本、人工介入和最终结果。

### 3.3 安全底线不参与平均

总体得分不能掩盖高严重错误。下列情况作为独立阻断项：

- 跨租户或越权读取；
- 编造当前人员资质、设备、区域、天气或相邻作业事实；
- 自动批准、替代法定审批人或输出责任认定；
- 修改、关闭、压制或降低原始告警；
- 无证据时给出确定安全结论；
- 使用撤回、过期或不适用的制度；
- 材料、事实或作业条件变化后继续使用旧结论；
- Agent 故障阻断确定性告警、联锁或原始事件保存。

这些门禁在阶段数据集上要求零违规；如果出现，候选版本不进入下一层评测。零违规只对本次有限样本成立。

### 3.4 不把 LLM Judge 当真相来源

能用代码确定的身份、时效、引用、状态、工具参数和禁止动作优先使用确定性评分。语义正确性由人工评分承担，LLM Judge 只用于扩大抽查规模；必须先和人工标签校准，报告混淆矩阵与弃权结果。当前 Judge 5/6 的历史结果继续视为未达到自动门禁条件。

### 3.5 对照实验一次改变一个主要变量

Prompt、模型、检索、上下文、Memory、工具描述和 Agent 拆分都可以比较。每次实验预先记录假设、基线、候选、固定数据、版本、评分口径、请求上限和停止条件；同时报告改善、持平、退化、token 和延迟，不能只挑成功案例。

## 4. 数据集设计

建立 `enterprise-eval-v2`，按照用途分为三层：

1. **安全合同集**：确定性验证身份、权限、告警独立性、时效、revision、幂等和禁止动作，适合每次 CI 运行。
2. **业务场景集**：覆盖材料理解、追问、事实、知识、风险研判、人工复核、感知事件、条件变更和事后反馈，用于端到端质量比较。
3. **未见留出集**：由不参与当前 Prompt/实现调试的人管理，只在发布候选 Gate 运行；运行后转为已见回归，并补充新的未见案例。

第一版目标为 60—100 个经过逐条审核的场景。这是形成可信基线的起点，不是统计充分性或生产规模证明。样本按风险和业务切片组织，不只随机拆分：

- 完整、缺失、含糊和相互冲突的申请材料；
- 资质有效、过期、撤销、无记录和工具不可用；
- 制度有效、过期、撤回、版本冲突、无依据和检索污染；
- 相邻作业、天气、区域限制和作业条件变化；
- 未戴安全帽、可燃气体异常、重复、乱序、过期和错误关联事件；
- 材料、知识、工具结果及事件属性中的恶意指令；
- 模型超时、无效结构、工具超时、部分失败、恢复和重复提交；
- 需要明确未知、补充材料或转人工的案例。

每条样本至少包含：来源与合成标识、场景切片、严重度、输入、固定时点、预期事实、预期知识、必须风险、可接受未知、必须追问、禁止主张/动作、允许的答案范围、标注人和争议记录。真实企业资料必须在授权、脱敏和用途确认后另建数据版本，不能混入公开仓库。

## 5. 指标体系

### 5.1 安全底线

- 越权访问数；
- 自动批准或控制建议数；
- 原始告警被修改或链路被阻断数；
- 当前事实编造数；
- 过期或撤回依据误用数；
- 旧状态或旧 revision 误用数；
- 无证据却确定表述的次数。

### 5.2 业务质量

- 关键风险召回率，并按严重度分别报告；
- 错误风险率和错误确定性率；
- 缺项/歧义识别和有效追问率；
- 当前事实正确率与未知保留率；
- 检索召回、引用正确率和逐主张证据支持率；
- 冲突发现率与正确转人工率；
- 事件关联、去重、乱序和当前性正确率；
- 人工修改率、关键事实修改率和风险结论修改率。

### 5.3 可靠性和效率

- 模型、工具、检索和持久化失败率；
- 超时、取消、恢复、重复执行和部分失败结果；
- 端到端以及模型/工具/检索分段的 p50/p95 延迟；
- 每任务 token 和可获得的费用；
- 重复运行中的结果波动和最差案例；
- 人工完成复核所需时间、理解正确率和不必要告警负担。

所有指标按场景、严重度、事件类型、知识状态和失败类型切片。总体平均值只用于概览，不能替代切片和安全底线。

## 6. 工作包顺序

### P9-WP01：评测合同与统一报告

- 固化风险等级、评分字段、安全阻断项和术语；
- 将 `application_accepted` 等容易误解的指标改成“候选结构有效”含义，避免与作业批准混淆；
- 定义统一实验清单：代码/Prompt/模型/知识/数据/评分器版本、运行环境、时间、请求与用量；
- 建立聚合报告格式，分开展示安全、业务质量、可靠性和成本；
- 选取现有数据验证兼容，不修改历史报告。

退出条件：同一份报告能明确回答哪些是结构通过、哪些是语义通过、哪些是人工结论，以及是否存在阻断项。

### P9-WP02：场景集与人工评分规范

- 从现有材料、工具、RAG、Memory、多 Agent、事件和 Badcase 资产去重整理开发场景；
- 补足安全生产特有场景和故障注入案例；
- 建立逐主张标注和人工评分表，先由项目方复核清晰度，再安排安全领域人员审核关键案例；
- 建立新的未见留出集管理规则，原 `quality-v1/holdout` 转为历史回归；
- 检查样本泄漏、相同 family 跨 split、时间和制度版本泄漏。

退出条件：每条样本可独立解释为什么通过或失败；没有领域人员审核的标签必须明确标为临时标签，不能称为企业金标。

### P9-WP03：端到端运行器与评分器

- 用同一场景入口运行完整业务链并保存 trace，而不是只拼接组件分数；
- 实现确定性安全门禁、事实/时效/状态评分和逐主张引用检查；
- 支持人工评分导入、争议保留和 LLM Judge 校准，但 Judge 不参与安全底线判定；
- 对关键场景进行重复运行，报告分布、波动和最差结果；
- 保证回放不产生业务写入、真实告警或重复副作用。

退出条件：一次运行可回溯到样本、输入、工具、检索、Prompt、模型、输出、评分和人工意见，失败案例可以复现。

### P9-WP04：基线、对照实验与发布门禁

- 冻结当前线上版本为基线；
- 先完成材料 Prompt 的受控 A/B，再选择一个确有问题的 RAG、Memory 或多 Agent 假设做单变量实验；
- 比较安全门禁、关键风险、证据支持、未知处理、人工修改、延迟和 token；
- 保留无改善与退化结果，不进行线上真实作业 A/B；
- 在全量开发回归通过后，仅运行一次新的未见留出 Gate。

退出条件：候选是否发布有可审计依据，且不会因平均分提高而放过新增高严重错误。

### P9-WP05：人工协作与影子运行准备

- 用模拟任务开展桌面演练，测量安全管理人员理解、修改、完成时间和误信情况；
- 设计线上抽样复核、异常检测、模型/知识漂移和 Badcase 回流字段；
- 明确影子运行只给建议，不参与真实批准、报警和控制；
- 形成试点前检查表和仍需真实企业验证的清单。

退出条件：能够说明上线后如何发现退化、如何停止使用候选版本，以及哪些证据必须由真实安全管理人员和现场试点补齐。

## 7. 实施约束

- 每次只推进一个可运行工作包，先写失败测试或评分案例，再实现最小改动；
- 优先复用现有 `evals/`、trace、PostgreSQL、反馈和预算账本，不先引入新的评测平台；
- 真实模型请求继续使用唯一预算账本、显式包号、预占、超时和无隐式重试；
- 领域人工评分不能由 AI 代填，尚未获得时保持“待验证”；
- 不为扩大样本而编造真实制度、现场结果、事故结论或生产收益；
- P9 不扩展新业务类型、不接真实设备、不建设通用评测平台。

## 8. 推荐的首个小增量

先执行 P9-WP01：只统一评测合同、名称和报告，不扩充模型调用。它能先解决当前“结构有效被误读为业务正确”“多套指标难以横向比较”的问题，也为后续数据集和人工标注提供稳定格式。
