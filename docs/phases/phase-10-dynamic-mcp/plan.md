# P10 企业动态 MCP 接入开发计划

> 状态：待实施。2026-10-15 用户确认规划方向，并明确要求“先不实现”。本次只落规划；不因历史持续执行约定自动启动编码、服务注册、部署或真实模型调用。
>
> 后续实施按工作包推进，使用 executing-plans 逐包执行和验证。本文件是阶段开发计划，具体编码步骤在对应工作包启动时按冻结合同细化。

**Goal:** 让企业通过配置和自定义 MCP 接入设备、承包商人员及作业票系统，安澜能动态发现工具、依据企业业务范围选择来源，并将结果用于带来源的辅助核查。

**Architecture:** 在现有固定工具链旁增加通用 MCP 注册表、连接管理、工具目录、企业对象解析与来源选择、业务合同校验和动态查询工作流。模型理解问题并选择所需能力，宿主依据可信企业配置约束对象、服务和执行；新增符合既有合同的企业 MCP 不要求修改安澜源码。

**Tech Stack:** 复用 Python、Pydantic、官方 MCP Python SDK、PostgreSQL、现有模型网关和 JSONL/OTLP 追踪；首版覆盖受控 stdio 和远程 Streamable HTTP。实施时核对锁定 SDK 的传输及 Schema 支持，不预先声称兼容所有 MCP 服务。

## 1. 与现有计划及实现的关系

- 本阶段作为独立 P10 后续增量，不将 P9 评测强化标为完成，也不扩写 P9“不接真实设备”的范围；跨阶段实际排期由后续实施安排确定。
- 当前 `tools/mcp.py`、`interfaces/mcp_server.py` 及 Java 门面只适配两项既有事实查询；它们继续作为历史回归基线。
- 当前 `llm/tool_model.py` 的工具 Schema、`workflows/tool_loop.py` 的白名单、预期参数和“全部工具均须观察”规则都是固定的。动态链另设工具模型与工作流，不把已有固定核验直接改成任意工具执行。
- 首批使用合成企业系统验证；企业真实系统、账号及资料在获得对应接入条件后另行联调，合成演示不记为企业上线。
- MCP 服务由企业事先开发并部署；动态注册表示安澜接入服务并发现能力，不表示模型自动生成、安装或执行任意服务代码。

## 2. 首批三个场景

### 2.1 设备查询：检验与故障核查

用户任务：“查一下二厂这次吊装使用的起重机，检验有没有到期，还有没有未关闭故障。”

首批能力：

| 能力标识 | 业务输入 | 核心结果 |
|---|---|---|
| `equipment.asset.query` | 厂区、设备编号 | 设备编号、名称、类型、所属厂区及台账状态 |
| `equipment.inspection.query` | 设备编号、查询时点 | 检验类型、检验日期、有效截止时间、原始记录 |
| `equipment.fault.query` | 设备编号、状态及时间范围 | 故障记录、未关闭状态、分页与结果完整性 |

企业可封装 ERP、EAM 或自建系统；内部 `asset_no` 等字段由企业 MCP 或声明式字段映射转换。编号未知时先请求补充或查询已授权目录，不由模型编造设备编号。设备“在用”与“检验有效”分别呈现；查不到、列表不完整或故障服务失败均不等于“无故障”。

### 2.2 承包商人员核查：资质、培训和准入

用户任务：“核查今天进入一厂的这家承包商和这批人员，资质、培训和准入是否齐全。”

| 能力标识 | 业务输入 | 核心结果 |
|---|---|---|
| `contractor.qualification.query` | 承包商编号、所需资质类别、查询时点 | 资质类别、状态、有效期及来源 |
| `person.training.query` | 人员编号、培训类别、查询时点 | 培训完成情况、适用范围及有效期 |
| `person.access.query` | 人员编号、厂区、查询时点 | 进场授权状态、适用厂区与有效窗口 |

姓名重名时解析到企业人员编号再查询；培训记录、承包商资质和进场授权是不同证据，不能互相替代。默认返回完成核查所需字段，日志及模型上下文不扩大收集身份证号等无关信息。

### 2.3 作业票查询：当前票据与交叉作业

用户任务：“查一下1工厂今天的动火作业票，附近有没有其他同时进行的作业。”

| 能力标识 | 业务输入 | 核心结果 |
|---|---|---|
| `permit.ticket.query` | 厂区、作业类型、时间窗口，可选票号 | 作业票编号、类型、区域、起止时间、原始状态及版本 |
| `permit.overlap.query` | 票号或标准区域编号、时间窗口 | 时间与区域重叠的候选作业、关联依据和结果完整性 |

企业须声明区域匹配方式，例如同一区域编号或明确提供的邻接关系；缺少区域关系时，安澜不能自行推断“附近”。时间重叠属于事实候选，不自动判定两种作业构成危险冲突。查询原系统的审批状态可以呈现，但安澜无审批、签发、撤票及控制接口。

## 3. 动态注册机制

首版由企业管理员通过可信管理入口注册，普通用户通过业务对话使用工具。管理入口先落管理 CLI，不借当前普通 Bearer 身份自动获得管理权限；后续管理 API/页面须另定义管理员权限。

注册记录包括：

- `server_id`、展示名称、配置版本、所属企业、服务负责人；
- 传输方式、受信远程地址或管理员配置的本地启动参数、`credential_ref`；凭据引用不等于凭据正文；
- 厂区编号与别名、所支持能力、工具绑定、能力合同版本；
- 主来源、历史分界或核对用途，以及显式配置的可用备用来源；
- 用户/角色及对象适用范围、超时、结果大小和调用限制。

流程：注册草稿 → 建立连接并初始化 → `list_tools()` 发现工具 → 校验业务合同与适用范围 → 管理员启用。

连接失败、合同不符或来源规则重叠未解决时，保留注册与诊断信息，但不向业务模型发布该绑定。通过协议连接、`readOnlyHint` 或服务自己的描述均不自动证明其权限或业务可信性。

工具按服务分配唯一别名，完整记录 `(server_id, original_tool_name)`。生成符合模型接口命名限制的别名并检测截断/编码碰撞，不只依赖两个字符串拼接。服务描述和返回内容作为数据处理，不能修改宿主指令、凭据或注册配置。

支持发现刷新、启停及配置版本更新；新发现工具及 Schema 变化先进入待验证状态，不因刷新自动扩权。一次查询固定目录和路由版本；禁用操作立即阻止新的分发，对正在执行的调用请求取消并拒绝发布被禁用后的迟到结果。

stdio 只运行管理员登记的本地程序，远程接入只连接登记且验证的目的地址。普通聊天文本不能成为 shell 命令、任意 URL 或租户凭据。每企业凭据和会话隔离，目录按身份和能力范围筛选。

## 4. 动态调用与多个同类 MCP 的选择

### 4.1 厂区识别与服务选择是连续两步

企业提供厂区目录及别名，例如：

| 厂区编号 | 企业确认的称呼 | 当前作业票来源 |
|---|---|---|
| `F001` | 一厂、第一工厂、1工厂 | `permit_legacy` |
| `F002` | 二厂、第二工厂、2工厂 | `permit_new` |

“1工厂”不是安澜全局内置的“一厂”同义词，只在该企业明确配置的目录中成立。模型提取用户原话中的厂区和业务意图，宿主在当前用户可访问的目录中解析、校验对象，再筛选允许使用的服务。模型可以在筛选后的能力目录内选择工具，不承担猜测数据权威来源的职责。

问题缺少厂区时，可使用明确配置且向用户展示的默认厂区。无默认值、别名匹配多个对象或目录无记录时，先澄清；查询时间同样按明确配置的企业时区解析并记录。

“查1工厂今天的作业票”的完整路径：

1. 模型识别作业票查询意图和原始称呼“1工厂”。
2. 可信企业目录解析为 `F001`，检查用户对该厂区的访问范围。
3. 来源规则选择 `permit_legacy`；记录原因与配置版本。
4. 将允许的工具 Schema 转成模型 Tool Calling 格式，生成并校验参数。
5. 通过对应 MCP 会话执行 `call_tool`，校验结果、对象、时点及来源。
6. 返回带来源的结果；证据不足则保留未知或追问。

### 4.2 两个服务覆盖同一业务范围

注册新服务不会自动覆盖旧服务，也不会仅按注册时间、名称相似度或模型偏好选择。管理员须配置以下关系之一：

| 关系 | 选择规则 |
|---|---|
| 替代 | 新服务负责当前查询，旧服务保留指定范围的历史查询 |
| 时间分工 | 按业务查询时间及明确分界选源；跨分界查询拆分并合并，标明各自范围 |
| 能力补充 | 一个负责票据主信息，另一个负责另一项明确能力 |
| 双源核对 | 用户明确提出核对或任务规则要求时查两边，分别呈现证据与差异 |

未配置关系而发生同范围竞争时阻止该绑定启用或返回“来源待确认”，不静默任选一个。同一对象在不同系统的编号映射由企业提供，不能仅凭相同编号认定为同一张票或同一台设备。

备用服务只有在明确授权、业务范围及数据时效满足要求时才可使用，输出必须标注降级和实际来源。连接成功但数据落后不能作为有效故障切换。双源冲突保留两条证据，不覆盖、不投票合成单一事实。

### 4.3 运行边界

- 工具目录由服务发现与权限配置共同生成；模型看见的工具与运行时可执行集合必须一致，执行时再次检查启用状态。
- 必查证据由任务能力要求决定，不能要求调用所有发现工具；无关设备、承包商服务不随作业票问题全部发送给模型。
- 默认单次查询最多 3 轮模型决策、6 次工具调用、60 秒；超过限制保留已取得证据及未完成项。工具默认超时 5 秒，仍受任务剩余时间约束；初始上限在验收中固定，不能由模型修改。
- 输入与上下文继续遵守现有网关及组装预算；单工具返回最多 64 KiB。分页在调用总额内进行，未取全必须标记，不能截断后称“全部”。
- 超时、断连、取消和无效结果分别保留原因；不隐式重试有未知语义的工具，不把失败解释为安全或不具备资质。
- 日志关联 tenant/user、task/run、服务、原工具名、合同/路由版本、来源选择原因、耗时及错误；凭据不写日志，正文按最小必要原则留存。
- 模型只通过原模型网关调用并使用既有唯一预算账本；真实实验须有合法工作包与可用额度，不借动态工具绕过预算。

## 5. 企业接入规范

### 5.1 两层兼容要求

协议兼容：支持所选传输、初始化、工具发现和调用；参数提供可校验 JSON Schema，结构化结果提供对应合同。首版只接受运行时校验器及模型适配器支持的 Schema 子集，不支持的结构明确拒绝，不静默删掉约束。

业务兼容：声明实现第 2 节中的哪些能力和版本，满足相应输入、输出、对象标识、时效、完整性及异常语义。协议连通不等于通过业务验收。

工具名称不强制相同。例如 `get_equipment_inspections` 与 `query_asset_check_records` 均可配置绑定到 `equipment.inspection.query`。

### 5.2 统一证据外壳与场景载荷

新增动态结果合同，不将任意结果硬塞进当前仅支持两个固定工具的 `ToolResult`。

| 字段 | 含义及校验责任 |
|---|---|
| `schema_version`、`capability`、`contract_version` | 企业 MCP 声明，安澜校验是否为登记合同 |
| `data_origin` | 明确合成或企业来源；服务声明及接入验证记录分别保留，不能仅凭返回文字认证为真实 |
| `objects`、`scope` | 对象编号及业务范围，与本轮授权请求匹配 |
| `queried_at` | 带时区的查询时点，与本轮请求语义一致 |
| `outcome`、`reason` | 明确 `ok/unknown/error`，区分无记录、过期、无权、超时和不支持 |
| `data` | 对应设备、人员或作业票的业务载荷，按能力合同校验 |
| `sources` | 原系统、原始记录编号、来源版本或更新时间及适用有效期；缺失项明确为空并影响可用性 |
| `complete`、`next_cursor`、`coverage` | 列表是否取全、分页位置及实际覆盖范围；完整空列表与未完成查询分开 |

安澜另附自身测得的服务标识、工具名、接收时间、调用标识、配置版本与响应摘要。这些宿主字段不能被服务返回的同名字段覆盖。接收时间和响应摘要不冒充原系统更新时间或原始记录版本。

各场景需固定状态枚举、时区、单位、有效期及空值语义。企业原状态与规范化状态同时可追溯；没有可靠映射时返回未知，不由模型自行转换为“正常”或“有效”。

### 5.3 企业定制交付步骤

1. 选择业务能力及合同版本，确认厂区、人员、设备、票据的编号及别名。
2. 编写自己的 MCP，调用本企业 IT 系统并完成复杂字段、状态和编号转换。
3. 简单字段路径或固定枚举映射可在版本化接入配置中声明；配置不执行 Python、shell 或自由表达式。复杂计算仍放企业 MCP。
4. 使用安澜接入模板和合同测试检查正常、无记录、无权、超时、过期、分页及冲突结果。
5. 管理员注册、试连接、查看发现工具，配置能力绑定和来源分工，再启用业务调用。

首批交付三类 MCP 合成参考服务、配置示例、合同 JSON Schema、契约测试及接入指南；示例全部使用假凭据引用和合成资料。

任意扩展工具可登记并查看发现结果，但首版业务执行只开放已通过能力合同的工具。新能力先增补合同和验证，再开放给核查工作流；不把任意文本工具自动提升为必查证据来源。
