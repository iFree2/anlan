# 安澜化工安全生产知识库建设与 RAG 服务方案草案

日期：2026-10-12。试点行业：化工与危险化学品。状态：研究与设计草案，供项目拆分和技术选型使用；其中模型、解析器和容量配置须经过真实文档对照测试再定版。本文交付建设路线图，不代表已经部署或达到企业生产验收。

目标是让安全生产 Agent 在确定的企业、装置、作业、权限和时点下，取得可定位、可核验、适用且完整的知识证据。建设范围包括文件接入、结构解析、分类切片、知识审核、混合检索、Agent 接口、版本维护和质量评测。

首批围绕动火与受限空间作业，贯通国家法律法规、相关标准、企业规程、作业流程、技术限值表和事故调查报告。随后按验收结果扩展到其他特殊作业、工艺安全、设备检维修和应急处置。

## 1 当前基础与需要补齐的能力

项目现有 `src/anlan/knowledge` 已提供本地中文向量、PostgreSQL 与 pgvector 检索、租户与读者过滤、版本替换、时效和撤回、原文引用，以及只读工具适配。这些能力可以作为兼容基线。

当前输入合同仅接受 SYNTHETIC JSON 段落；`store.py` 每 360 字符切分；`embeddings.py` 固定 BGE small 中文模型与 512 维；所谓 hybrid 是向量候选上的中文双字重合度重排。尚无 Word、Excel、PDF、图片直接接入，无条款树、表格结构和原页定位，也没有真实企业语料的检索验收。

生产升级必须同时处理知识合同、身份权限、上下文和证据输出中的 SYNTHETIC 约束，不能只取消上传端的标记。现有合成链路与历史评测保留，新服务采用独立版本合同和索引代次，逐步替换。

## 3 总体架构与三种建设路径

推荐保留安澜的 Python、FastAPI、LangGraph 和 PostgreSQL 基础，将文件处理与在线 Agent 解耦。摄取是异步任务，在线检索只访问已审核发布的数据。

```text
授权来源 / 企业上传 / 文件系统与文控连接器
                  ↓
接入登记与内容去重 → 原文件对象存储
                  ↓
格式识别 → 原生解析 / OCR / 专项表格与图片解析
                  ↓
统一结构化表示 → 质量检查 → 业务分类切片
                  ↓
元数据与适用性审核 → 建立待发布索引 → 发布代次
                  ↓
PostgreSQL 管理版本、权限、审核、任务和发布清单
OpenSearch 提供关键词、向量与元数据过滤检索
                  ↓
知识服务 → Agent 取得证据 → 主张引用校验 → 人工复核
```

| 路径 | 适用情况 | 代价与建议 |
| --- | --- | --- |
| 自建受控服务，复用安澜 | 需要条款效力、装置适用性、审核发布和与现有工作流深度结合 | 推荐路径。需要开发文档治理和评测，但能控制知识与权限合同 |
| RAGFlow 等平台加自有治理服务 | 希望快速验证文件上传、解析预览和检索效果 | 可作对照试验或后台组件。必须实测权限、条款定位、时效、撤回和 API；不能以平台支持格式代替业务验收 |
| 商业文档解析与检索服务 | 有外发授权和预算，希望减少解析运维 | 可为难解析文档提供备选。需评估数据驻留、合同、调用成本、可追溯定位及停服替换能力 |

RAGFlow 官方配置区分通用、手册、表格等解析方式，可作为平台方案候选，见 [RAGFlow 知识库配置](https://ragflow.io/docs/v1.0.0-rc1/dataset_configuration)。不同时建设多个完整 RAG 平台。

## 4 多格式文件的解析方案

文件格式决定如何解析；业务类型决定如何切片。一个事故报告可能是 Word、扫描 PDF 或图片，最终都应得到相同类型的结构和业务字段。

| 文件类型 | 首选处理方式 | 必须保留的内容 | 质量检查和失败处理 |
| --- | --- | --- | --- |
| DOCX | Docling 原生转换；需要时用 python-docx 与 OOXML 专项适配 | 标题层级、自动编号、段落、表格、图片、备注；修订与批注单独识别 | 未接受的修订标记进入审核；正文位置用段落或 XML 锚点，不能编造页码 |
| DOC 等旧 Office | 隔离环境通过 LibreOffice 转换，再解析 | 原文件、转换产物、转换器版本及对应关系 | 不运行宏和外部链接；转换失败显式记录 |
| TXT / Markdown | 显式编码检测与解码、段落及标题解析 | 原字节、编码、行号、标题、列表 | 乱码、解码不确定或空内容进入待处理队列 |
| XLSX / CSV | openpyxl 等原生单元格适配，Docling 表格转换作为对照 | sheet、逻辑表、多级表头、合并区域、单位、脚注、单元格范围、公式和缓存值 | 不把整个 workbook 拼成一句文本；公式与缓存值不一致或缺失时标记未知 |
| XLS | 受控转换或 xlrd 适配，与 XLSX 流程衔接 | sheet 和单元格原位置 | 转换改变数值、日期或合并关系时拒绝直接发布 |
| 数字 PDF | Docling 的布局与文本解析为首选候选，必要时用 pdfplumber 等交叉核验 | 阅读顺序、章节、页码、段落边框、表格、图片及脚注 | 分页检测文本质量；有文字层不代表其文字可靠 |
| 扫描或混合 PDF | 按页检测，扫描页采用 PaddleOCR PP-StructureV3；MinerU 作复杂版式对照 | 原页图、识别文字、坐标、阅读顺序、表格关系、识别质量信息 | 低清晰度、错序、表格断裂、关键数字疑似错误进入人工校对 |
| PNG / JPEG / TIFF 等文档图片 | 图像预处理后 OCR 和版面分析 | 原图、文字区域、方向、图题及关联文档 | 手写、模糊图、盖章遮挡不强行转成可信知识 |
| 流程图、装置示意图、图表 | 保留原图与邻接文字；必要时用视觉模型辅助抽取节点、关系与说明 | 图像定位、图例、方向、设备标签、推导说明的生成来源 | 描述和关系属于辅助抽取，需专家确认后用于工艺与操作依据 |

Docling 官方支持 PDF、DOCX、XLSX 和多种图片等格式，旧版 Office 转换依赖 LibreOffice，见 [支持格式](https://docling-project.github.io/docling/usage/supported_formats/)。PaddleOCR 的 PP-StructureV3 提供布局、表格和文字等解析能力与细粒度坐标，见 [官方项目](https://github.com/PaddlePaddle/PaddleOCR)。这些是组件能力，表中化工审核规则是本项目设计。

解析器不互相重复处理所有文件。优先原生结构，按页或区域补 OCR，疑难文档再进入备选解析器。一个文件的所有处理结果都关联原文件 hash 与解析流水线版本。

采用独立 Linux worker 环境验证文档库、OCR 与 GPU 依赖兼容性，避免直接把全部依赖加入现有 Python 3.13 在线服务。在线接口与 worker 通过版本化合同通信。

### Excel 的业务分流

规程附表、技术限值、检查清单模板可以进入知识库；人员资质、当前检测记录、设备状态和日常作业台账应进入关系数据库与只读事实工具。静态的历史台账快照可以归档供案例分析，但必须标明时点，不能替代当前事实。

`openpyxl` 不负责重新计算公式。需要计算结果时，优先由可信业务系统提供经过核验的值；受控重算作为独立任务，记录引擎和版本，不执行任意宏。照片中的安全标识与现场图像观察也要分开，后者有采集时点且不自动成为制度条款。

## 5 统一结构化表示与来源定位

所有解析器输出统一的 `DocumentIR`，基本层次为文档 → 章节 → 内容块。内容块类型包含 heading、paragraph、list、table、figure、footnote，每块保存父节点、顺序、原文、来源位置和质量标记。

来源位置按格式表达：PDF 为页与 bbox；DOCX 为段落或 XML 锚点；Excel 为 sheet 和单元格范围；TXT 为行号或字节位置；图片为图像与 bbox。Word 如需按页查看，生成固定渲染预览并保存原锚点到预览页的映射，不能认为源 DOCX 天生有稳定页码。

保存两份内容：`source_text` 用于引用和核验，`retrieval_text` 用于检索，后者可补文档标题、章节路径、标准编号、术语别名。空格规范化和单位标准化记录映射，不直接改写源文中的数值、否定词和符号。OCR 转录关联原页图并标明人工确认状态；原文匹配只能证明转录一致，不能证明 OCR 没有读错。

统一输出 JSON 为权威中间结果，Markdown 用作预览和部分检索串行化。表格同时保存结构化 cells 或 rows 和 HTML 表示，图片单独保存；不把 Markdown 当成唯一源数据。

## 6 按业务类型切片

### 法律法规与标准

建立篇、章、节、条或条款编号树，以完整条款为基础。适用范围、术语定义、引用条款、附录和表格作为独立结构节点，保存引用关系。一个条款的适用条件、例外和列举项应一起保留。

超长条款先按完整子项分成子片段，保存 `parent_id`，命中后在预算内补完整父条款与依赖条件。必要依赖无法装入上下文时返回“证据包不完整”，而不是只保留一句义务句。跨页是布局边界，不应自动成为条款边界。

区分规范性正文、规范性附录、资料性附录、标准解释与培训解读，分类结果经审核。文档类型与发布机构提供判断依据，但法规、强制性要求、推荐性标准和企业规程之间的适用与冲突由专业人员制定政策，不能只按一个“权威分”自动裁决。

### 企业操作规程与 SOP

以步骤或有依赖的一组步骤为单元，绑定对象、前置条件、执行动作、责任岗位、注意事项、禁止条件、结束条件与异常处置。检索一个动作时同时扩展必要的前置步骤和警告，保持原顺序。

企业规程的工厂、装置、设备型号、工艺版本和岗位是显式适用字段。尚未确认适用范围的文件可以归档和检索预览，但不能作为装置操作依据正式发布。

### 表格

小表整体保留；大表按逻辑行组切分，每组带完整多级表头、单位、适用条件及相关脚注。跨页续表需校验是否确为同一表格；合并单元格展开时保存原结构，避免条件列与数值列错配。

需要精确筛选、统计或数值比较的表格，同时生成可查询的结构化数据，查询由代码执行。RAG 用来发现表格和解释语义，计算结果附单元格来源。不能只让向量检索回答“某装置全部限值是否超标”。

### 事故调查报告

以事故为父实体，按基本情况、事件经过、直接原因、间接原因、责任分析、整改与防范措施分别组织。保存行业、工艺、物料、设备、作业类型、事故时间和报告机构等字段。

事实、调查机关认定与后续分析要区分。命中原因片段时可补事故背景与关键经过。事故整改措施属于该报告的经验与结论，不能自动改写为所有企业适用的法定义务。

### 切片参数与上下文补全

首轮实验以子片段 300、500、800 tokens 为候选，使用实际 embedding tokenizer 计算；这些是实验参数，不是固定行业标准。结构完整的短条款可更小；表格和父段按结构和上下文预算处理。

不跨条款机械加入固定百分比 overlap。自然长文本可以使用小幅重叠作为对照；法规与 SOP 优先利用父子关系和显式依赖扩展。片段 ID 绑定文档版本、结构路径、内容 hash 和切片版本，防止流水线变化却复用旧引用。

模型生成的文档摘要、关键词、事故标签和图片说明保存为衍生数据，附生成模型与审核状态。检索增强文本不能作为原文引用。

## 7 知识目录与版本治理

建立法规标准、企业制度规程、技术资料、事故案例四个逻辑集合，可以共用存储，但有各自的适用条件、审核流程和检索策略。企业生产台账仍由业务数据服务管理。

| 元数据组 | 主要字段 | 用途 |
| --- | --- | --- |
| 文档身份 | logical_document_id、document_version_id、标题、文号或标准号、发布机构、source_uri、文件 hash | 区分同一规范的不同版本及同版本的扫描或电子副本 |
| 效力与版本 | 文档类型、规范性质、发布日期、生效日、失效日、状态、替代关系、修订单、已核验时间 | 当前检索、历史时点检索和更新核验 |
| 适用范围 | 行业、地域、企业、厂区、装置、设备、物料、工艺、作业、岗位 | 决定是否可为当前任务提供依据 |
| 权限与发布 | tenant、组织或用户组、保密级别、owner、审核人、发布代次 | 全链路授权与审核追责 |
| 内容定位 | 章节路径、条款编号、页、bbox、sheet、cells、parent_id、依赖节点 | 原文追溯和上下文补全 |
| 数据血缘 | parser、OCR、chunker、embedding、reranker、配置 hash、校对记录 | 重建、质量归因与版本对照 |

文档的“正式内容版本”、文件副本版本、解析版本和检索索引版本分别管理。同一份标准的清晰 PDF 和扫描副本可以归为同一内容版本，原文件依然分别留存，不将所有副本重复放大排名。相似内容跨文档去重时保留来源和效力差异。

正式文献可能没有失效日期，字段应允许为空；缺失生效时间则进入审核，不通过猜测补齐。部分修订、替代和废止应支持条款级变化。建立业务有效时间与系统登记时间，按作业时点选择当时适用的版本；“最新上传”不能等同“当时有效”。

权威来源优先采用 [国家法律法规数据库](https://flk.npc.gov.cn/search)、[全国标准信息公共服务平台](https://std.samr.gov.cn/)、应急管理部门正式发布以及企业文控系统。平台目录可用于状态核验，全文获取遵守授权范围，不能假定所有标准都允许批量下载、复制或再分发。

首批标准目录可纳入 GB 30871-2022。2026-10-12 查阅 [国家标准全文公开系统条目](https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=561B95121C30853A6B45CA9471F39239&refer=outter) 标示现行；这条状态在采集与发布时仍应重新核验。该条目确认标准身份与状态，不替代完整正文授权及逐条适用性审核。

## 8 RAG 检索与 Agent 服务

### 检索流程

1. 可信宿主传入身份、任务、材料版本、作业时点与已知装置条件。模型不能伪造 tenant、角色和授权策略。
2. 识别请求类型：条款精确查找、主题问答、规程步骤、技术表格、案例研究、版本对比。关键适用条件缺失时提出业务追问，或者将结果明确标为待确认适用性。
3. 标准号、文号、条款号走精确字段检索；主题问题同时进行 BM25 与向量召回。两路执行同一权限、发布时间状态、效力与业务范围策略。
4. 结果融合采用 RRF 等排名融合基线，再对有限候选使用 cross-encoder 重排。首轮对照召回每路 30 与 60 条、重排 30 与 60 条、最终 5 与 10 条；以覆盖率、延迟和成本选择，不直接照搬外部 top_k。
5. 扩展完整父条款、必需条件、表头脚注和明确引用的定义。扩展节点与原图附件同样重新检查权限、版本和时效。
6. 组装证据包，返回已核验适用依据、待确认适用依据、案例参考、冲突和缺证。复合问题按子问题检查证据覆盖，不让高相似度单片段掩盖缺项。
7. Agent 按主张引用证据，宿主校验引用 ID、连续原文、版本与来源位置。语义支持由专家标注评测和复核补充，不能只靠字符匹配判定安全建议正确。

检索分数不作为“答案正确概率”。现有统一 0.45 相似度阈值需替换为按问题类型校准的支持判定和缺证机制。多轮检索使用固定白名单、次数、deadline 与候选预算；保留首次问题，改写不得改变标准号、数值、否定和作业条件。

### Agent 接口

建议定义三类只读工具：

- `search_safety_knowledge`：输入问题与可信业务上下文，返回证据包。
- `get_safety_clause`：根据受限文档版本与条款 ID 取得原文和允许扩展的上下文。
- `query_safety_reference_table`：根据注册表、字段和受限筛选条件返回结构化行与单元格来源。

权限身份来自宿主执行上下文，不出现在模型可填的参数中。允许的企业、装置和时点由宿主校验。工具不能接受任意 SQL、路径或 URL。当前 `query_knowledge` 作为兼容适配器，不直接向旧合同塞入长表和新字段。

证据包至少包含 `evidence_id`、`document_version_id`、条款或内容块 ID、原文、定位、适用范围、效力核验信息、原文件 hash、处理版本、审核状态、请求时点、索引代次和缺证原因。查询审计还记录召回方式、过滤策略版本、候选与最终选择、重排模型以及延迟。

检索服务返回证据，回答与行动由业务工作流处理；知识库不能替代当前检测值和资质记录。需要完整检查清单的请求，应先确定所需证据类别，再进行检索与覆盖检查，不能把 Top 5 自动当成全部要求。

### 权限与跨系统一致性

PostgreSQL 是权限、效力、审核与发布清单的权威来源，OpenSearch 是可重建检索投影。BM25、向量、父子扩展、表格查询、原文件预览和缓存全部受同一策略约束。

索引候选先过滤，向重排器、生成模型或调用者传递之前再核对权威状态。权限收紧或文档撤回应先在权威状态中生效并使相关缓存失效，异步更新索引；索引未同步时，旧候选被最终校验拒绝。缓存键带身份权限摘要、适用上下文、时点与发布代次，不复用其他租户结果。

## 9 技术栈建议与选型实验

| 层次 | 推荐候选 | 决策方式 |
| --- | --- | --- |
| 原文件存储 | 现有阿里云部署可选择 OSS；私有化选择企业现有 S3 兼容存储 | 保留源文件和预览，权限下载；核对数据驻留、版本与备份要求 |
| 文档与治理数据 | PostgreSQL | 复用项目基础，新增文档资产、结构块、审核、适用性、任务与发布代次 |
| 解析 | Docling 统一适配，Word 与 Excel 增加原生专项处理 | 同一套真实样本对照 Docling、Unstructured，按格式统计准确性与耗时 |
| 中文扫描与复杂版面 | PaddleOCR PP-StructureV3 与 MinerU | 首轮对照后选择主引擎，难文档保留备选路由，不默认全量运行两套 |
| Embedding | 保留 BGE small 基线；BGE-M3 为升级候选 | 专业词、编号、长条款检索效果与资源成本联合比较 |
| Reranker | BGE reranker v2 m3 为候选 | 与无重排基线比较相关性、关键证据覆盖与 P95 延迟 |
| 企业检索 | OpenSearch 的 BM25、向量与过滤 | 推荐生产试点目标。现有 pgvector 留作兼容与基线，不重复建设两套生产向量索引 |
| 异步处理 | 起步用 PostgreSQL 任务与独立 worker；需要时引入 Celery 与 Redis 等队列 | 先具备任务幂等、租约、重试和失败记录，吞吐压测后再增加队列组件 |
| API 与工作流 | FastAPI、现有 LangGraph | 保留现有预算、超时与取消，知识服务用独立合同接入 |
| 质量与观测 | pytest、领域题库、现有 Trace 与 Jaeger | 解析、检索、回答分别评分；记录血缘并按租户脱敏日志 |

OpenSearch 官方提供 [混合检索](https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/index/) 与 [带过滤的向量检索](https://docs.opensearch.org/latest/vector-search/filter-search-knn/efficient-knn-filtering/) 能力。需要对选定发行版、中文分词器、分析器与融合实现锁版本并实测。标准号保存 keyword 精确字段与规范化别名，避免中文分词破坏编号。

轻量实验可以先保留 pgvector 并在小数据上做可替换 BM25 基线；若验证 pgvector 路径足够满足容量与延迟目标，可以调整生产选型。PostgreSQL 自带全文检索不直接等同中文 BM25。使用 HNSW 时还需实测过滤后召回不足的问题，官方提供迭代扫描和分区等方法，见 [pgvector 过滤与迭代扫描](https://github.com/pgvector/pgvector#iterative-index-scans)。

BGE-M3 官方模型卡标示 dense 输出 1024 维、最长 8192 tokens，见 [模型卡](https://huggingface.co/BAAI/bge-m3)。升级需新建对应索引并完整重编码，不能向现有 512 维字段写入，也不能混合不同模型向量。模型能力不替代专业领域评测；长上下文能力也不意味着必须采用大切片。

[BGE reranker 官方模型卡](https://huggingface.co/BAAI/bge-reranker-v2-m3) 可用于本地重排选型。CPU、GPU、批量和并发配置以测量确定，暂不承诺某种显卡即可达到指定吞吐。

MinerU 当前 [许可](https://github.com/opendatalab/MinerU/blob/master/LICENSE.md) 为 Apache 2.0 基础上附加条款，包括商业规模门槛与对外服务标识义务。采购与发布前核对锁定版本的代码、模型权重和依赖许可；“开源”不能直接视为无条件商用。

暂不把 GraphRAG、全面知识图谱、模型微调和多模态向量库列为首期必选。先用关系表管理条款引用、替代、步骤依赖和事故属性；如果评测证明跨标准或跨事故多跳查询明显不足，再单独立项验证图检索。

## 10 文档建立与维护流程

### 文件从接入到发布

接入登记 → 原文件归档 → 格式解析 → 结构与内容质量检查 → 元数据和适用性审核 → 切片与索引构建 → 抽样复核与回归 → 发布。

上传、解析、审核、索引准备和发布分开记录。解析成功不等于正式可用。文件损坏、加密、编码错误、转换失败、OCR 质量不足或关键字段不完整时进入明确的待处理状态，界面展示原因和处理人，不以空片段冒充成功。

文件检测、大小与页数限制、压缩炸弹检查、隔离转换和宏禁用放在接入边界；正文中的指令按数据处理。原始文件和派生文件分别授权，不把自动识别出的内部路径当作可访问 URL。

### 版本更新与撤回

新内容先进入待发布代次；完成解析、审核、索引清单核对和回归后切换。PostgreSQL 与 OpenSearch 不宣称单一数据库事务，用发布清单、任务 outbox、幂等索引写入及对账处理跨系统一致性。

发布失败保留旧已批准代次，失败产物不对外提供。正式撤回与权限收紧先阻止继续使用，再清理索引、缓存和父子扩展结果。回滚索引版本时仍执行最新的撤回和权限策略，不能复活已撤回文档。

原文件 hash 不变且处理配置不变时不重复解析；处理算法变化产生新解析代次，法规内容版本不变。增量改版根据受影响条款重建，并检查引用它的条款、SOP、清单和历史证据包。

旧报告保存当时证据快照和索引代次，用于追溯；文献修订后标记受影响报告需要重核。历史回放区分“当时可见依据”和“现行依据”，默认不得把旧报告当成当前操作依据。

### 维护职责与频率

| 角色 | 责任 | 推荐节奏 |
| --- | --- | --- |
| 企业文控 | 企业规程版本、发布、替代、适用装置、保密级别与全文授权 | 文控变更事件触发；每周对账未处理变更 |
| 安全与标准负责人 | 法规标准目录、效力核验、条款适用、关键内容审核、金标准答案 | 官方来源允许时每日检查公告或版本变化；每周处理待确认项 |
| 数据工程 | 接入、解析路由、结构修复、去重、增量重建与发布清单 | 每日检查失败队列；按文档类型抽样 |
| 后端与运维 | 检索、权限、任务恢复、监控、备份和容量 | 监控失败与延迟；每月恢复和撤回演练 |
| 业务 QA | 关键问题回归、引用与适用性抽查、Badcase 归因 | 每次发布与组件升级；每月整理新增业务问题 |

官方来源没有稳定接口时采用受控人工登记，不承诺自动抓取全网。频率是维护建议，不自动创建调度任务。法规复核过期后，针对该来源返回状态待核验；保留可追溯原文但不假定其仍现行。

## 11 验收方法与建议门槛

首轮建立约 120 份经授权真实文件和 300 道业务问题，覆盖法规标准、SOP、限值表、事故报告以及 DOCX、TXT、XLSX、数字 PDF、扫描 PDF 和图片。数量是启动建议；按实际类别补齐，尤其保留低清扫描、跨页表、复杂表头、旧版和部分修订的样本。

其中建议 60 道作为封存留出集。调参前划分开发集和留出集，同一文档的副本、近重复题和同一业务案例放在同组，避免泄漏。答案标注必须包括全部必要证据、条件、例外、时点和允许的缺证响应。安全专家审核，不能只让生成模型和评测模型自评。

| 验收层 | 指标与建议目标 | 解释 |
| --- | --- | --- |
| 解析 | 逐格式记录文字错误、章节顺序、表格单元格准确性；关键数字、单位、比较符、否定、例外和定位在必测样本中零错后发布 | 不用整体 OCR 字符准确率掩盖危险内容错误；有错则修复或阻止该内容发布 |
| 条款查找 | 精确编号题在冻结测试集命中正确版本与条款 100% | 编号检索应走明确字段，测试通过不代表所有未来题都正确 |
| 检索 | 建议必要证据集合 Recall@20 ≥ 95%，同时报告“全部必需证据都召回”的问题比例 | 按场景和格式分组，复合题不能只命中一个片段就算通过 |
| 权限与效力 | 越权、未发布、撤回、历史时点错配和回滚复活在边界测试中零泄漏 | 同时测试检索、重排输入、上下文扩展、缓存、原文件和图片预览 |
| 回答 | 每个知识主张有可定位引用；专家评分的语义支持率建议 ≥ 95% | 分别记录条件遗漏、错用单位、把案例当规定等错误；关键不受支持主张阻止发布 |
| 缺证与冲突 | 高风险缺证题和已标注冲突题必须明确保留未知或冲突 | 不能以流畅回答补齐依据；宽泛“没有要求”视为错误 |
| 性能 | 在指定硬件、语料代次和并发下，首轮以知识检索 P95 ≤ 3 秒为目标 | 包含查询编码、召回、重排和证据组装，不含回答模型；超时预算与现有 5 秒工具边界协调 |
| 运维 | 更新、撤回、任务重跑、索引对账、恢复与回滚演练通过 | 记录更新发现到发布的分段耗时，区分机器时间与人工审核时间 |

以上是建议验收门槛，不是业界统一标准或已取得成绩。投产前由业务负责人和工程负责人据风险、容量与硬件确定。样本零错误不能推导总体绝对安全；严重错误进入阻断与人工复核流程。

初始容量分别记录文档数、页数、片段数、每日增量、并发、存储和模型内存。不要根据文件数量猜配置。成本报告分列解析每页、重排每问、生成每问、对象存储、索引、GPU 和人工校对，以采购预算与评测收益决定是否扩容。

对照顺序：现有 360 字符向量基线 → 结构切片 → 确定性上下文补全 → BM25 加向量融合 → 重排 → 父子和依赖扩展。固定题集与内容版本，逐步消融，记录收益和代价；评估解析器时再联合验证最终召回，避免只比 OCR 平均分。

## 12 分阶段建设计划

建议 10 至 14 周完成首个受控试点。估算假设有两名工程人员、一名数据或 QA 人员及持续参与的化工安全专家，已取得试点资料和部署资源。单人实施或资料授权尚未完成时，应按交付物安排，不作固定日期承诺。

| 阶段 | 参考周期 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 0 目录和评测准备 | 1 至 2 周 | 动火与受限空间场景清单、权威来源登记、真实样本、问题与证据金标准、数据授权范围 | 格式和业务类别有代表样本；开发与留出划分冻结；专家确认答案 |
| 1 多格式接入与解析 | 2 至 3 周 | 原文件资产管理、任务状态、格式路由、DocumentIR、原页或单元格定位、解析预览、解析器对照报告 | 首批各格式均可处理或明确拒绝；关键内容可校对；失败可恢复 |
| 2 业务切片与治理 | 约 2 周 | 条款与步骤树、表格块、事故案例块、元数据、适用性、审核与发布、版本及修订关系 | 专家确认切片与来源；版本、撤回、历史查询和权限边界测试通过 |
| 3 混合检索与证据服务 | 约 2 周 | BM25 与向量、编号检索、融合、重排、父子扩展、证据 API、离线报告 | 必要证据召回达标；逐格式与复合题缺陷归因；满足测试硬件延迟目标 |
| 4 Agent 与业务试点 | 约 2 周 | 三类只读工具、任务适用上下文、主张引用校验、缺证追问、事实与知识联合复核 | 旧链路回归通过；真实题有正确适用依据与引用；异常保留已有事实 |
| 5 运维验收与扩展决策 | 约 1 周 | 更新、撤回、缓存失效、任务恢复、备份、回滚和索引重建演练，维护职责与成本报告 | 通过冻结留出和边界测试；业务负责人签署试点范围后再扩展目录 |

各阶段可并行准备资料和测试，但文档审核、发布与接口验收按依赖顺序进行。推进以阶段条件为准，未通过时先修复并复测，不能靠增加模型规模跳过解析或治理缺陷。

### 现有项目的模块落点

以下路径是拟新增或拆分的设计，尚未实施。按阶段分别形成可执行小计划，避免一次性修改全部工作流。

| 模块 | 拟定位置 | 职责 |
| --- | --- | --- |
| 文档资产与中间合同 | `src/anlan/knowledge/documents/` | 原文件、版本、DocumentIR、位置与质量合同 |
| 解析适配 | `src/anlan/knowledge/parsing/` | router、文本、Office、PDF、OCR 适配与统一输出 |
| 业务切片 | `src/anlan/knowledge/chunking/` | 法规条款、SOP、表格、事故报告及父子引用 |
| 治理与发布 | `src/anlan/knowledge/governance/` | 适用性、效力、审核、发布代次与更新影响 |
| 检索适配 | `src/anlan/knowledge/retrieval/` | 编号、BM25、向量、融合、重排与证据扩展 |

上线使用新的内容与索引空间，先离线对照、再影子检索、后小范围切流。影子阶段不重复触发真实生成模型和付费请求。依赖锁定、打包资源、接口合同与原有预算校验纳入回归；不为新知识实验复用或重置既有模型授权额度。

## 13 首轮优先交付

第一轮优先完成三件事：建立经授权的真实多格式样本与领域金标准题库；完成原文件保留、结构解析、关键内容校对和来源定位；确定条款、SOP、表格与事故案例四类切片规范。

达到这些条件后，再对比模型、重排器和检索引擎。后续扩展范围与资源采购由对照结果决定，持续维护围绕文献更新、权限变化和业务 Badcase 驱动。
