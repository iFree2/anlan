# 安澜对话式业务查询设计

## 1. 背景与目标

当前双角色协作已经具备两条私有会话和一份共享申请：申请人和安全审核人员只能读取自己的会话消息，双方通过受限业务投影查看同一份申请。现有 `ChatResponder` 虽然能收到任务投影，但没有专门的业务查询合同；例如用户询问“当前材料状态是什么”时，当前实现通常将其归为 `casual_chat`，scripted 模式只能提示以侧栏为准。

本设计增加“确定性查询路由 + 只读查询网关”，使 Agent 能在不修改业务状态、不暴露对方私聊的前提下，回答当前申请状态、申请详情、流程解释和动火安全知识问题。

核心原则：

- 业务状态只来自当前授权的权威数据；
- 安全知识只来自可引用的知识库证据；
- 证据不足时明确说明未知，不使用模型常识补齐；
- 只读问题不得产生材料修改、协作命令或状态迁移；
- 共享的是业务事实，不是产生这些事实的原始对话。

## 2. 范围与非目标

本期包含：

- 当前申请状态、材料版本、缺失字段和当前处理方查询；
- 作业位置、作业对象、作业方式、附件说明等申请详情查询；
- 基于当前状态机的下一步和失败原因解释；
- 带知识库引用的动火安全知识问答；
- 查询权限、字段投影、证据合同、查询审计和回归评估；
- 为后续 `business-query` Skill 预留稳定的只读接口。

本期不包含：

- 将完整业务权限或状态计算迁移到 Prompt、Skill 或脚本；
- 允许 Skill 脚本直连 PostgreSQL；
- 使用模型通用知识补充无依据的安全结论；
- 共享双方私聊、隐藏推理、内部错误或完整历史材料快照；
- 因查询自动绑定、创建、修改、提交、批准或授权开工；
- 第一阶段发布完整 Skill 包。

## 3. 总体架构

查询链路拆分为三个独立组件：

```text
用户消息
  -> BusinessQueryRouter
  -> ReadOnlyQueryGateway
  -> EvidenceBundle
  -> AnswerComposer
  -> 私有会话回答
```

### 3.1 BusinessQueryRouter

路由器只生成结构化查询决策，不访问数据库、不回答问题、不产生写入。决策至少包含：

```json
{
  "query_type": "application_status",
  "target_task_id": "task-123",
  "sub_questions": ["material_status", "missing_fields"],
  "classifier_version": "business-query-v1"
}
```

宿主必须对模型候选施加确定性约束。问句、否定、假设、引用和知识咨询不能被静默转换成业务写入；显式写动作继续使用现有待确认命令和版本校验。

### 3.2 ReadOnlyQueryGateway

网关是业务查询的唯一可信入口，负责：

- 解析服务端认证身份和协作角色；
- 校验租户、任务归属、申请参与关系及当前阶段；
- 在任务锁内读取一致的当前材料、协作状态和预核查投影；
- 按角色执行字段白名单过滤；
- 解释固定状态机规则；
- 执行有界知识检索并保留引用；
- 生成版本化证据包并记录最小查询审计。

第一版提供四个稳定能力：

```text
query_application_status
query_application_details
query_process_guidance
query_safety_knowledge
```

这些能力复用现有材料服务、协作访问策略、预核查服务和知识检索，不复制其权限与状态规则。

### 3.3 AnswerComposer

回答器只能读取 `EvidenceBundle`，不能访问原始数据库对象、另一参与者的会话或内部执行状态。

- 状态和详情查询优先使用确定性模板；
- 流程解释使用当前状态与固定状态机规则生成；
- 安全知识允许模型归纳，但关键结论必须对应知识引用；
- 证据不足、知识服务失败或引用无效时不得退化为模型猜测；
- 状态和详情模板失败时使用安全的固定兜底，知识问答失败则明确失败。

## 4. 查询类型与路由规则

| 查询类型 | 示例 | 数据来源 | 是否允许写入 |
|---|---|---|---|
| `application_status` | 当前材料状态是什么？轮到谁处理？ | 当前材料与协作投影 | 否 |
| `application_details` | 作业对象是什么？还缺哪些材料？ | 授权后的结构化字段 | 否 |
| `process_guidance` | 下一步怎么办？为什么不能提交？ | 当前状态与固定状态机 | 否 |
| `safety_knowledge` | 为什么需要气体检测？ | 授权知识检索及引用 | 否 |
| 现有业务写意图 | 补充位置、提交、要求整改 | 现有工作流与协作命令 | 仅确认后 |

路由规则：

1. 询问表达默认只读，不能顺便修改材料。
2. 一条消息同时包含查询与写请求时，先执行只读查询；写请求生成独立的待确认候选，二者不得共用一个隐式动作。
3. 只读查询不要求二次确认，但必须经过权限校验并记录查询结果。
4. 查询失败不得降级到通用聊天模型编造业务事实。
5. 不明确属于查询还是写入时，保持只读并要求用户澄清。

## 5. 目标申请解析

目标任务按以下顺序解析：

1. 用户明确指定申请编号：校验权限后查询。
2. 当前会话已绑定申请：查询该申请。
3. 当前会话未绑定且用户只有一个可访问申请：返回该申请的有限摘要并要求明确选择，不自动绑定。
4. 用户有多个可访问申请：返回有限、分页或有界的摘要列表并要求选择。
5. 用户没有可访问申请：说明暂无可查询申请，并提示其角色允许的下一步。

选择申请本身是私有会话动作。除非用户通过既有受控接口明确绑定，否则查询不得改变 `active_task_id`。

## 6. EvidenceBundle 合同

网关返回统一、版本化、可审计的证据包：

```json
{
  "schema_version": "business-evidence-v1",
  "query_type": "application_status",
  "task_id": "task-123",
  "material_revision": 3,
  "application_version": 2,
  "observed_at": "2026-11-01T10:30:00+08:00",
  "facts": [
    {
      "key": "application_status",
      "value": "changes_requested",
      "source": "collaboration_application"
    },
    {
      "key": "missing_fields",
      "value": ["attachment_description"],
      "source": "material_checkpoint"
    }
  ],
  "citations": [],
  "allowed_actions": ["edit_materials", "resubmit"],
  "limitations": []
}
```

证据包必须包含查询时间和适用的材料、申请版本。知识问答的关键事实必须绑定引用标识；状态类事实必须绑定受控数据源标识。

证据包不得包含：

- 对方聊天消息、待确认意图或会话 ID；
- Prompt、隐藏推理、模型原始输出；
- 内部运行 ID、错误堆栈、密钥或连接信息；
- 未经授权的历史材料快照；
- 与当前问题无关的个人信息；
- 权限过滤前的完整数据库记录。

## 7. 回答合同

最终回答包含：

- 简明自然语言答案；
- 申请编号；
- 读取时的材料版本和申请版本；
- 查询时间；
- 知识问答所需的引用；
- 必要的限制或数据不可用说明。

状态回答示例：

> 申请 task-123 当前处于“要求补充”状态，材料版本为 3。作业位置、对象和方式已填写，附件说明仍缺失。你可以补充附件说明后重新提交。本结果读取于 2026-11-01 10:30。

回答不得声称“批准”“准许开工”或其他超出当前业务边界的结果。`review_completed` 只解释为材料核查完成。

## 8. 权限与信息隔离

查询网关沿用现有服务端认证身份和 `collaboration_role`，不得接受客户端自报角色。

- 申请人只能查询自己的申请；
- 安全审核人员只能查询明确分配给自己的、已提交的申请；
- 同租户未分配审核人员、其他申请人和跨租户身份统一拒绝；
- 无权访问统一表现为“申请不存在或当前身份无权访问”，不泄露资源存在性；
- 双方使用同一查询接口，但网关按角色生成不同的字段投影和允许动作；
- 查询回答写入提问者自己的会话，不生成给对方的聊天副本；
- 协作通知只传递允许共享的业务事件，不传递查询问题或回答。

历史工作流查询保持 owner-only。审核人员能看到的历史仅限刻意公开的协作事件、版本号和业务载荷，不开放完整 checkpoint 历史。

## 9. 一致性、错误与降级

- 查询必须在授权任务锁内读取材料与协作元数据，避免组合不同版本的数据。
- 如果回答生成前检测到版本变化，重新读取一次；第二次仍不稳定则返回冲突并提示刷新。
- 无活动申请时返回可访问申请摘要并要求选择。
- 无知识依据时返回“当前知识库没有足够依据”。
- 知识服务不可用时明确暂时不可查询，不调用通用模型补齐。
- 状态和详情回答器失败时使用确定性模板兜底。
- 知识回答器失败或引用校验失败时不返回未经验证的半成品。
- 查询不得创建 pending intent、材料 operation、协作 command、协作 event 或 notification。

## 10. 查询审计

增加最小查询回执，记录：

```text
actor、role、task_id、query_type、source_message_id
material_revision、application_version、evidence_schema_version
citation_ids、outcome、queried_at
```

查询审计不重复保存完整问题文本，也不保存完整证据包；原问题已经存在提问者自己的私有会话。审计表和日志不得成为新的跨角色消息共享渠道。错误记录使用稳定分类，不保存敏感原始异常。

## 11. Skill 演进策略

第一阶段将能力抽离为应用内独立查询内核，并预留稳定只读接口，不立即发布完整 Skill。查询内核稳定且出现多 Agent、多入口复用需求后，再增加薄 `business-query` Skill 适配层：

```text
business-query/
├─ SKILL.md
├─ schemas/
│  ├─ query-request.json
│  ├─ evidence-bundle.json
│  └─ answer-envelope.json
├─ scripts/
│  ├─ query_application_status
│  ├─ query_application_details
│  ├─ query_process_guidance
│  └─ query_safety_knowledge
└─ tests/
   └─ contract-cases.json
```

Skill 约束：

- 脚本只调用认证后的只读 HTTP 接口；
- 脚本不直连数据库，不复制权限、状态机和字段过滤逻辑；
- Skill 只负责能力说明、工具选择和结果呈现；
- API Schema 与 Skill 分别版本化；
- 新问题类型先扩展查询内核，再升级 Skill；
- Skill 旧版本必须忽略未知可选字段，不能因新增字段解析失败。

## 12. 测试与验收

### 12.1 合同和单元测试

- 查询决策、证据包和回答合同拒绝未知或越界字段；
- 询问、否定、假设、引用和提示注入保持只读；
- 混合查询与写请求拆分为回答和独立待确认候选；
- 状态与详情模板只使用证据包字段；
- 知识回答缺少引用时验证失败。

### 12.2 权限与隔离测试

- 申请人和指定审核人员只能查询各自允许的数据；
- 未分配审核人员、其他申请人和跨租户身份不可查询；
- 回答中不出现对方聊天、待确认意图、Prompt、Trace 或完整历史 checkpoint；
- 显式猜测他人 task/conversation ID 不泄露资源存在性。

### 12.3 状态与并发测试

- “当前材料状态是什么”不增加材料或申请版本，不生成业务命令；
- 返回的状态、缺失字段、允许动作和版本与同一锁内快照一致；
- 查询期间版本变化时不输出混合版本答案；
- 无目标、单个候选、多个候选和无候选分支符合目标解析规则。

### 12.4 知识与评估测试

- 每个安全知识关键结论都有可访问、当前有效的引用；
- 无结果、授权撤销、过期引用和知识服务失败均安全拒答；
- 建立状态、详情、流程、安全知识、歧义、多意图、越权和提示注入评估集；
- 如后续发布 Skill，脚本、Schema 和服务接口必须通过契约测试。

### 12.5 验收标准

1. Agent 的每个业务事实均可追溯到当前授权数据或知识引用。
2. 任何只读问题都不会引起业务状态变化。
3. 任何角色都无法通过问答看到对方私聊或未授权历史材料。
4. 回答明确标注目标申请、数据版本和读取时间。
5. 无依据或服务失败时明确拒答，不生成貌似可信的业务结论。

## 13. 后续交付顺序

设计批准后另行形成实施计划，建议按以下依赖顺序分批：

1. 查询合同、路由约束与评估样例；
2. 只读网关、权限投影和证据包；
3. 状态、详情和流程的确定性回答；
4. 带引用的安全知识问答；
5. 查询审计、并发与全量回归；
6. 稳定后再评估并实现 Skill 薄适配层。

本设计不授权直接进入实现；实施任务、文件归属、测试命令和发布边界由后续计划文档确定。

具体编码、测试和交付必须在新的独立 Codex 聊天中执行。当前设计聊天只负责固化设计与实施计划，不在同一聊天内启动实现；新聊天开始前必须读取本设计及后续计划，并以独立检查点回报实施结果。
