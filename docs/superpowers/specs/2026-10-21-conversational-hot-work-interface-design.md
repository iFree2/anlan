# 安澜动火作业对话入口设计

日期：2026-10-21
状态：设计已由用户确认，等待书面规格复核；尚未实施。

## 1. 背景与目标

安澜现有操作台以材料表单、任务列表和后端响应面板为主。虽然已经具备动火材料分析、缺项追问、任务恢复、事实与知识核验、感知事件和人工反馈能力，但交互仍像传统业务网页，没有形成统一的 Agent 对话体验。

本次改造目标是提供一个统一对话入口：

- 用户以自然语言与安澜交流；
- 系统识别普通闲聊、疑似动火申请和当前任务补充等意图；
- 疑似动火申请必须经过二次确认，确认后才创建现有材料任务；
- 动火流程中的缺项追问、补充、修订、恢复和核验继续复用现有工作流；
- 普通闲聊可以临时打断工作流，但不丢失当前任务；
- 页面采用“对话窗口 + 任务侧栏”，而不是在聊天窗口中继续堆叠原始接口 JSON。

本次只改变交互入口和编排层，不重写动火业务工作流，不增加新的作业类型，也不扩大为通用 Agent 平台。

## 2. 已确认的产品原则

### 2.1 交互形态

桌面端以对话为主要操作区，右侧任务侧栏持续展示：

- 当前任务类型和状态；
- 材料版本；
- 已获得字段与仍缺少的字段；
- 事实、知识和事件核验状态；
- 暂停、恢复或切换任务所需的明确入口。

移动端将侧栏折叠为可展开的任务面板。原材料表单不再作为首要入口；必要的结构化信息以对话追问、确认卡片和侧栏详情呈现。

### 2.2 二次确认

意图模型识别到疑似动火申请时，系统只创建待确认意图，不创建业务任务。安澜先复述自己的理解，例如：

> 我理解你可能要申请一项动火作业：明天在一号罐区 V101 管线进行补焊。是否进入动火作业申请流程？

只有用户明确确认后，策略门才允许调用现有 `start` 能力。用户否认时丢弃该候选，继续普通对话；用户改口时更新候选并再次确认。

### 2.3 可打断、可恢复

动火任务进行中时：

- 普通闲聊和解释性问题可以直接回答；
- 回答后可以轻提示当前任务仍在等待什么，但不能强迫用户立即完成；
- 明确的材料补充映射到当前任务；
- 可能既是闲聊又是材料补充的消息必须先澄清，不能静默写入；
- 用户可以显式暂停，之后从服务端最新版本恢复；
- 用户提出另一项业务申请时，系统先确认新建还是切换，不能覆盖当前任务。

一条会话同一时刻最多绑定一个活动任务，但可以保留多个历史或暂停任务。

## 3. 方案选择

采用“受控路由器 + 现有工作流”。

没有采用单一 Agent 全包方案，因为它会把闲聊、意图判断和业务写入混在同一个模型循环中，误触发难隔离、难评测。当前也不采用 Supervisor 多 Agent，因为第一版只有普通对话和动火申请两个主要方向，引入多 Agent 会增加延迟、成本和故障面。未来增加受限空间、吊装等独立专业流程后，可重新评估 Supervisor，但专业 Agent 仍不能绕过统一策略门。

## 4. 总体架构

系统分为三层。

### 4.1 交互层

- `Chat Timeline`：显示用户消息、助手回复、意图确认卡片、工作流进展和错误状态。
- `Task Sidebar`：显示当前任务的只读投影，不直接持有业务规则。
- `Composer`：提交一条自然语言消息，每次提交生成稳定 `request_id`。

### 4.2 对话编排层

新增以下边界清晰的组件：

- `ConversationService`：保存会话、可见消息、活动任务、待确认意图和路由结果；协调一次消息处理。
- `IntentClassifier`：根据当前消息、有限会话上下文和活动任务状态，返回结构化意图候选与字段候选；不持有业务写工具。
- `PolicyRouter`：用确定性代码处理二次确认、活动任务、暂停、切换、版本和权限；它是唯一允许调用业务适配器的入口。
- `ChatResponder`：生成普通回复；不持有材料、事件或审批类写工具。
- `WorkflowAdapter`：将策略门批准的动作映射到现有材料服务的 `start`、`resume`、`revise` 和 `recover`，并把现有任务状态转换为对话消息与侧栏投影。

### 4.3 业务层

沿用现有 `MaterialService`、材料 LangGraph、PostgreSQL 任务、revision、幂等提交、恢复、事实与知识核验、事件和人工反馈能力。对话层不复制这些业务规则，也不直接修改材料表。

核心边界是：模型只能提出候选，只有 `PolicyRouter` 在身份、确认、状态和 revision 均满足时才能通过 `WorkflowAdapter` 产生业务写入。

## 5. 意图合同

第一版只定义满足当前产品所需的有限意图，不建设通用意图库：

| 意图 | 含义 | 允许动作 |
| --- | --- | --- |
| `casual_chat` | 普通闲聊、解释性问题或与当前任务无关的对话 | 调用 `ChatResponder`，不修改业务任务 |
| `hot_work_candidate` | 可能希望申请新的动火作业 | 创建或更新待确认意图，不创建业务任务 |
| `confirm_pending_intent` | 明确确认待处理的动火意图 | 策略校验后创建现有材料任务 |
| `reject_pending_intent` | 否认或取消待确认意图 | 丢弃候选，返回空闲对话 |
| `task_input_candidate` | 可能是在补充或修订当前任务 | 根据当前缺项和字段合同判断；歧义时要求确认 |
| `pause_task` | 暂时停止当前会话对该任务的引导 | 解除活动状态但保留任务和历史 |
| `resume_task` | 恢复一个暂停或历史任务 | 先读取服务端最新状态，再设为活动任务 |
| `switch_or_create_task` | 请求另一项业务任务 | 要求用户明确新建或切换，不能覆盖当前任务 |

分类输出包含意图、是否需要确认、字段候选、可向用户说明的简短依据和分类器版本。不得保存或展示隐藏推理过程。置信状态只用于策略分支，不向用户展示伪精确概率。

## 6. 会话状态机

### 6.1 空闲对话

普通消息直接进入闲聊。疑似动火消息进入 `pending_confirmation`，系统复述候选内容，不创建任务。

### 6.2 等待意图确认

- 确认：使用已确认候选创建材料任务，进入 `active_hot_work`；
- 否认：丢弃候选，返回空闲对话；
- 改口：更新字段候选，继续等待确认；
- 其他问题：可以回答，但待确认状态保持可见。

### 6.3 动火任务进行中

- 明确补充：经字段合同校验后调用 `resume` 或 `revise`；
- 普通闲聊：回答后保持活动任务；
- 歧义补充：先展示拟写入内容并询问确认；
- 暂停：会话进入 `paused`，业务任务本身保留；
- 新任务：询问新建还是切换，不复用旧 `request_id`。

### 6.4 暂停状态

恢复时先读取任务最新 revision。任务已被其他会话更新时，侧栏展示最新状态，不能用暂停前的旧 revision 自动重放。取消只解除对话绑定；不伪造业务审批、材料关闭、事件关闭或报警状态变化。

## 7. 数据设计

建议新增独立的会话存储，不把聊天消息塞入现有材料任务快照。最小数据对象包括：

- `conversations`：归属、状态、revision、活动任务和待确认意图引用；
- `conversation_messages`：用户或助手可见消息、提交顺序、消息状态和关联 `request_id`；
- `conversation_routes`：分类器版本、结构化路由结果、实际执行分支、关联业务对象和错误类别；
- `pending_intents`：独立保存待确认类型、字段候选、来源消息、版本、确认结果和失效状态，以不可变修订记录保留更新审计；`conversations` 只引用当前有效候选。

每个对象继承可信服务端身份范围。会话消息不作为企业事实、制度依据或长期用户记忆；材料字段只有经过策略门和现有服务校验后才进入业务任务。

刷新或跨进程恢复所需的显式状态包括 `conversation_id`、可见消息、`active_task_id`、待确认意图、路由结果、会话 revision 和消息 `request_id`。不得依赖浏览器内存恢复权威状态。

## 8. HTTP 与事件契约

浏览器面向对话层，而不是自行选择现有业务接口。建议最小接口为：

- `POST /conversations`：创建空会话；
- `GET /conversations/{id}`：读取会话、消息和任务侧栏投影；
- `POST /conversations/{id}/messages`：提交用户消息，包含 `request_id` 和 `expected_revision`；
- `GET /conversations/{id}/stream`：推送会话和任务投影变化；
- `GET /conversations`：列出当前用户最近会话。

消息提交结果包含更新后的 conversation revision、新增可见消息、路由状态和任务侧栏投影。对于处理中断但已保存接收回执的消息，应能按 `request_id` 定位并显式恢复或返回已有结果。

第一版不以逐 token 输出为目标，而推送可恢复的语义事件：

- `message_received`；
- `intent_confirmation_required`；
- `workflow_started`；
- `task_updated`；
- `assistant_completed`；
- `operation_failed`。

现有任务、事件和核查 SSE 可以保留兼容，但新页面主要订阅会话流。逐 token 流式输出可在状态和幂等正确后另行设计。

## 9. 侧栏投影

侧栏由服务端根据活动任务生成只读投影，至少包含：

- 任务类型、task id、状态和材料 revision；
- 已获取与待补充字段；
- 最近一次分析模式和语义状态；
- 事实、知识和事件核验状态；
- 是否存在恢复、并发冲突或结果过时提示；
- 可执行的有限 UI 动作，例如暂停、恢复或查看依据。

侧栏不直接展示全部原始 JSON；完整证据、来源和历史通过按需详情查看。所有按钮仍调用对话或受控业务接口，不能在前端伪造状态迁移。

## 10. 模型与预算边界

闲聊、意图分类和现有动火分析是不同模型用途，分别记录调用类型、版本、延迟、结果类别和预算归属。是否复用同一供应商不影响它们的职责隔离。

当前在线 DeepSeek 预算已有既定限制。本设计不默认为无限闲聊授权，也不重置或绕过现有账本。实施计划必须在编码前明确新增调用的工作包、单包上限、失败计数和用户可见降级策略。在线预算耗尽时明确返回不可用，不切换到替身并冒充真实模型结果。

## 11. 失败与恢复

- 分类器失败或输出不符合合同：不创建或修改任务，返回安全的澄清回复；
- 闲聊模型失败：保留用户消息，显示可重试状态，不影响活动任务；
- 工作流失败：保留已有 task id 和提交回执，使用现有恢复语义，不伪造成功消息；
- 重复消息：同一 `request_id` 和相同载荷返回原结果，不重复创建任务或重复调用模型；
- 同一 `request_id` 不同载荷：拒绝；
- 旧 conversation revision 或旧 task revision：拒绝写入并返回最新投影；
- 同一会话存在处理中消息：后续写入返回明确冲突或排队状态，第一版不做隐式并行；
- 页面刷新或服务重启：从 PostgreSQL 恢复会话、消息、待确认意图和活动任务；
- 身份越权：对会话、任务、消息、事件和证据统一拒绝，不能通过侧栏投影泄漏存在性；
- 提示注入：用户消息与检索内容都是数据，不能改变策略门、身份、工具白名单或确认规则。

## 12. 测试与评测

### 12.1 合同与状态测试

覆盖普通闲聊、明确动火、疑似动火、确认、否认、改口、当前任务补充、歧义补充、暂停、恢复、新任务和任务切换。所有模型响应使用结构化替身验证控制流，不把替身结果算作真实模型质量。

### 12.2 安全门测试

必须验证：

- 未确认时不产生业务任务；
- `casual_chat` 不修改任何业务状态；
- 闲聊模型没有业务写工具；
- 歧义补充在确认前不写入；
- 旧 revision、越权、重复请求和同 id 不同载荷均正确拒绝；
- 取消或暂停不改变审批、原始报警或既有人工决定。

### 12.3 PostgreSQL 集成测试

跨进程验证会话、消息、待确认意图、活动任务和路由记录恢复。确认创建后，对话侧栏必须与现有任务读取结果保持一致。模拟模型返回后、会话落盘前和业务 checkpoint 前后的中断，记录允许的重复调用边界。

### 12.4 浏览器端到端测试

至少验证以下主链：

> “明天去罐区补焊” → 二次确认 → 创建任务 → 缺项追问 → 自然语言补充 → 临时闲聊 → 回到任务 → 刷新页面 → 看到同一任务最新状态。

同时验证桌面与移动布局、键盘发送、防重复提交、处理中状态、错误重试、历史会话选择、侧栏折叠和无障碍焦点顺序。

### 12.5 意图路由评测

建立版本化开发集与未见留出集，至少覆盖闲聊、明确动火、隐式动火、否定、反问、知识咨询、当前字段补充、多意图、提示注入和相似但非动火的维修描述。报告：

- 动火意图召回率；
- 闲聊误触发率；
- 模糊输入进入二次确认的比例；
- 当前任务字段提取准确率；
- 未经确认产生业务写入的次数，该项必须为零；
- 分类器与 Prompt 版本变化前后的逐场景回归。

总体平均值不能掩盖误创建任务等高风险错误。线上第一阶段采用影子记录或严格二次确认，不声称意图识别已达到生产准确率。

## 13. 实施范围与顺序

建议后续计划拆成以下小增量：

1. 定义会话、路由和投影合同，建立数据库迁移与替身测试；
2. 实现持久化 `ConversationService` 与确定性 `PolicyRouter`；
3. 接入结构化 `IntentClassifier` 和无写权限的 `ChatResponder`；
4. 实现复用现有服务的 `WorkflowAdapter`；
5. 增加会话 HTTP/SSE，并完成幂等、恢复和并发测试；
6. 将现有操作台替换为对话窗口与任务侧栏；
7. 建立路由数据集、浏览器 E2E、真实模型小样本和影子评测；
8. 验证后再决定是否增加逐 token 输出、附件输入或其他高风险作业类型。

不在本阶段建设语音、实时视频、通用工具市场、任意多 Agent 调度、完整审批系统或新的真实设备接入。

## 14. 完成标准

本功能只有在以下条件同时满足时才算完成：

- 用户可以只通过对话完成一条动火材料的创建、确认、缺项补充、恢复和查看；
- 任务侧栏与后端权威状态一致，刷新和重启后可恢复；
- 闲聊可打断但不会修改或丢失当前任务；
- 所有动火创建和歧义写入都经过明确确认；
- 重复提交、并发、越权、模型失败和恢复路径有自动化证据；
- 意图路由有版本化评测报告，未经确认的业务写入为零；
- 现有材料、事件、核查和历史任务回归通过；
- 真实模型结果、替身控制流和个人学习掌握继续分开报告。
