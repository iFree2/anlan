# 安澜 2.0 记忆与上下文管理分析

> 梳理日期：2026-11-19<br>
> 范围：基于当前工作区实现，讨论安澜 2.0 的记忆与上下文能力，以及开发企业级 Agent 时的重点和难点。

## 原始问题

1. 安澜 2.0 在 Agent 记忆和上下文管理方面，有哪些亮点和值得说道的地方？
2. 开发一款企业级 Agent，记忆和上下文管理的重点和难点在哪里？

## 总体结论

安澜 2.0 最值得讲的不是“它能记住多少”，而是它已经形成了企业 Agent 记忆治理的基本骨架：

**分层、有来源、先候选后确认、带版本和时效、可删除、受权限约束、按预算组装上下文。**

当前实现是“受控偏好记忆 + 会话工作记忆 + 事实/知识上下文”，还不是通用长期记忆平台。但这个边界反而更接近企业真实需求，也更容易讲清记忆系统应有的权威关系。

一句话概括：

> 它展示的不是“让 Agent 记更多”，而是“让 Agent 只在正确权限、正确时间、正确来源下记住正确的东西”。

## 一、安澜 2.0 的信息分层

安澜没有把任务状态、聊天记录、业务事实、企业知识和用户偏好混成一套“记忆”。

| 信息类型 | 安澜中的处理方式 | 能否作为权威事实 |
|---|---|---|
| 当前任务状态 | LangGraph checkpoint、任务 revision、活动任务 ID | 可以，但由业务代码解释 |
| 会话上下文 | 最近 12 条可见消息、待确认意图、脱敏任务投影 | 只用于理解交互 |
| 用户长期偏好 | 详略程度和呈现顺序两个枚举值 | 不能，只影响呈现 |
| 业务事实 | 工具按当前时间查询，带来源和有效期 | 可以，必须来自本轮查询 |
| 企业知识 | 带租户、读者、版本、时效和原文引用的检索结果 | 可作为依据，但不是审批权限 |
| 操作审计 | Memory revision、会话路由、查询回执 | 不进入模型上下文 |

这套划分让“记忆”不能替代当前事实、企业制度、任务状态或权限授权。

## 二、有代表性的实现亮点

### 1. 记忆不是模型自由写入的

[memory/store.py](../../../src/anlan/memory/store.py#L87) 把记忆写入设计成受控状态机：

`反馈登记 → candidate → 确认/拒绝 → active → 修正/冲突/过期/删除`

主要约束包括：

- 来源版本和内容 SHA-256 由宿主计算，模型不能伪造来源。
- 反馈先形成 candidate，只有明确确认后才变成 active。
- 修正会重新回到 candidate，而不是直接生效。
- `expected_revision` 防止并发修改和旧请求覆盖。
- 当前状态与不可变 revision 在同一事务中写入。
- 删除保留 tombstone，旧来源不能把已删除记忆静默复活。
- 查询同时约束租户、用户、active 状态和有效期。
- 过期记录在读取时立即过滤，不依赖后台清理任务。

相关设计见 [ADR006](../../decisions/006-user-memory-lifecycle.md#L3)。

核心姿态可以归纳为：**少记、晚确认、证据入账、可撤回**。

### 2. 长期记忆范围很小，但不是玩具 CRUD

当前长期记忆仅允许：

- `detail_level`：`brief` / `detailed`
- `presentation_order`：`unknowns_first` / `sources_first`

字段白名单定义在 [memory/contracts.py](../../../src/anlan/memory/contracts.py#L8)。范围虽然小，但已经包含来源、版本、生命周期、冲突、过期、删除和隔离。

这也是一个重要取舍：先证明记忆治理链路，再扩大记忆类型。没有自由文本提取，也没有让模型直接决定保存什么。

### 3. 上下文是编译结果，不是聊天记录拼接

“上下文编译”不是把信息排版得更整齐，而是围绕六个问题制定模型输入的准入规则：

| 聚焦问题 | 要防止的情况 | 安澜的处理 |
|---|---|---|
| 授权 | 跨租户、跨用户、跨角色信息泄漏；模型把无权限数据当事实 | 校验身份和范围；任务状态采用字段白名单投影，不把完整任务和原始证据交给模型 |
| 时效 | 使用过期偏好、旧任务版本、失效知识或当前不相关的记忆 | 检查状态、时间窗口、任务类型和用户归属；过期项标记 `expired_or_future`，冲突项标记 `conflict` |
| 容量 | 直接截断，导致未知项、错误或关键证据被悄悄删掉 | 区分必需和可选内容；必需内容超过预算时拒绝模型请求，而不是继续生成 |
| 结构 | 消息、知识、记忆和任务状态混在一起，模型分不清来源和用途 | 固定结构分层，明确系统边界、任务、事实、知识、偏好和历史各自是什么 |
| 权威 | 聊天文本说任务已提交，但数据库实际没有提交 | 上下文只是快照；任务状态以服务端为准，模型不能通过文本声称完成任务 |
| 审计 | 答案错了，但不知道是记忆召回、权限过滤还是上下文裁剪造成的 | 记录上下文版本、字节数、SHA-256、片段包含/排除原因和大小 |

目标是让模型只看到该看的，并能解释为什么看到或没有看到某一条信息，而不是尽可能塞入更多内容。

任务复核使用的 [context/assembly.py](../../../src/anlan/context/assembly.py#L64) 有明确装配优先级：

1. 固定系统边界和版本化业务指引；
2. 当前材料、事实、未知、错误与来源；
3. 有效的知识原文；
4. 有效用户偏好；
5. 历史摘要。

其中前两类是必需内容。必需部分超过预算时，系统直接拒绝模型请求，不会悄悄删除未知项。可选内容被裁掉时，会记录原因：

- `budget`
- `expired_or_future`
- `conflict`
- `scope`
- `invalid`
- `disabled`
- `irrelevant`

结果是系统既能解释“模型看到了什么”，也能解释“为什么没有看到某一条信息”。

相关设计见 [ADR007](../../decisions/007-bounded-review-context.md#L3)。

### 4. 对话上下文与证据上下文分开

对话侧在 [llm/conversation.py](../../../src/anlan/llm/conversation.py#L115) 只序列化：

- 最近 12 条可见消息；
- 当前待确认意图；
- 白名单内的任务投影；
- 当前协作角色。

整个上下文限制在 16 KiB。任务投影还会经过字段白名单，原始证据、隐藏推理和未授权字段不会顺便进入模型。

任务状态始终以服务端状态为准，模型不能依靠上下文声称任务已经创建、批准、更新或恢复。

### 5. 不同职责使用不同的最小上下文

安澜没有把所有能力塞给一个“万能模型上下文”：

- 意图分类器无工具，只做有界分类；
- 闲聊响应器无工具、无业务写能力；
- 任务复核先固定采集事实/知识，再由一次模型综合；
- 证据复核使用独立上下文，不传偏好、历史或材料全文。

这些边界减少了上下文污染，也降低了模型把数据当指令、把候选当授权的机会。

### 6. 状态恢复是上下文管理的一部分

企业 Agent 不能只在浏览器里“记住”上下文。安澜将以下内容持久化到 PostgreSQL：

- conversation revision；
- 活动任务；
- 待确认意图；
- 路由结果；
- 消息 `request_id`；
- 消息处理状态。

同一请求重放返回原结果；旧 revision 被拒绝；进程重启后，会话和任务关联仍可恢复。

知识查询在重放时还会重新检查材料版本、申请版本或引用是否仍有效，避免把旧上下文当新事实。

### 7. 协作共享不会偷走对方私聊

双角色协作只共享申请、材料、人工补充要求和公开事件，不共享普通聊天、推理痕迹和私有证据。

模型看到的是经过白名单投影后的共享状态，而不是把双方原始会话直接拼接在一起。这是企业 Agent 很实际、也经常被低估的安全边界。

### 8. 对“记忆是否有效”保持了诚实

真实消融中：

- 无记忆接受率：2/3；
- 有记忆接受率：2/3；
- 有记忆多使用 755 token；
- 没有证明质量提升。

负数结果和失败样本被保留在[真实消融报告](../../phases/phase-03-memory-context/evidence/wp03/live-report.md#L7)。

企业系统最怕的不是暂时没有记忆能力，而是把“多召回一些内容”包装成效果提升。安澜当前至少没有这样自欺。

## 三、当前能力的明确边界

安澜 2.0 目前不是完整的企业级长期记忆平台，主要表现为：

- 长期记忆只有两个枚举偏好，没有自由文本兴趣、人物关系和复杂情景记忆。
- 没有自动记忆抽取、语义去重、记忆合并、遗忘曲线和向量召回。
- 对话历史主要是最近 12 条加字节裁剪，没有摘要压缩；长会话中的早期约束可能丢失。
- 预算按 UTF-8 字节计算，是保守工程边界，不是精确 token 预算。
- 删除是 tombstone 加不可见读取，不能直接宣称满足生产隐私合规。
- 任务、知识、记忆不是跨存储的单一快照事务；目前通过版本复核和冲突拒绝降低混版风险。
- 本地身份仍包含模拟身份入口，不能等同于已完成生产认证和真实数据治理。

因此准确表述是：

> 安澜 2.0 已经证明企业级记忆治理的最小骨架，但不能说已经完成企业级长期记忆平台。

## 四、企业级 Agent 的重点

### 1. 明确什么有资格成为记忆

偏好、事实、知识、承诺、任务状态和组织规则必须有不同权威和生命周期，不能都存进一个向量库。

需要为每类信息定义：

- 类型；
- 所有者；
- 作用域；
- 来源；
- 可信度；
- 生效和失效时间；
- 敏感级别；
- 保留期限；
- 冲突策略；
- 检索权限。

### 2. 把记忆写入当作治理流程

重点不是“能不能写”，而是：

- 谁产生；
- 依据什么产生；
- 是否需要用户确认；
- 如何防止重复和污染；
- 新旧冲突如何处理；
- 什么时候失效；
- 错误记忆如何修正和撤回。

推荐路径：

`事实/反馈 → 记忆候选 → 来源校验 → 权限与敏感信息检查 → 去重/冲突检测 → 确认或确定性规则 → active`

### 3. 回答时选择真正有用的信息

相关性不等于有用性。记忆进入上下文前还要考虑：

- 当前任务是否相关；
- 是否属于当前用户或团队；
- 是否仍在有效期；
- 是否与当前事实冲突；
- 是否比当前权威信息等级更低；
- 是否包含敏感信息或提示注入。

### 4. 将上下文视为受版本控制的编译结果

企业上下文通常应包括：

- 目标；
- 当前角色和权限；
- 当前任务状态；
- 本轮事实与未知；
- 可用证据；
- 相关长期记忆；
- 输出合同。

必须明确：

- 哪些片段不可裁剪；
- 哪些可以摘要；
- 哪些只能引用；
- 哪些绝不能发送；
- 预算不足时应该降级还是拒绝。

### 5. 保持可恢复、可审计和可解释

每次回答应至少可以追溯：

- 使用了哪些记忆；
- 每条记忆的来源和版本；
- 使用了哪些知识和事实；
- 哪些片段因为预算、权限、时效或冲突被排除；
- 当时看到的是哪个任务版本。

## 五、企业级 Agent 的主要难点

### 1. 错误记忆比没有记忆更危险

模型一次错误抽取可能被长期复用。写入质量的优先级应高于记忆召回率和“记住多少”。

### 2. 冲突是常态

新旧偏好、不同部门规则、同一事实的不同版本可能同时存在。系统应显式保留冲突和来源，而不是让模型强行综合出一个唯一答案。

### 3. 权限会动态变化

检索后、生成前权限可能被收回。不能只在索引或检索阶段做 ACL，关键输出前还要重新校验。

### 4. 时间、事实和权限是三个问题

“曾经正确”“现在正确”“对当前角色可见”是不同判断，不能用一个字段混合表达。

### 5. 压缩可能导致证据断链

摘要必须保留来源范围和不可丢失的约束、未知项。否则越省 token，越容易产生没有依据的结论。

### 6. 删除是分布式问题

主库删除相对容易，缓存、向量索引、会话快照、备份和下游派生摘要才是真正难点。

### 7. 上下文故障难以归因

答案错误时，需要判断问题来自：

- 模型推理；
- 记忆写入；
- 记忆召回；
- 知识检索；
- 权限过滤；
- 时效判断；
- 上下文裁剪；
- 任务版本不一致。

### 8. 评测不能只看接受率

至少要覆盖：

- 错误记忆被采用率；
- 过期记忆泄漏率；
- 记忆召回准确率和覆盖率；
- 跨租户、跨角色泄漏；
- 删除传播完整性；
- 未知项保留率；
- 回答支持率；
- 成本和延迟；
- 无记忆/有记忆消融；
- 用户纠正后的收敛情况。

## 六、如果继续演进安澜 2.0

优先建议如下：

1. **增加长会话层级摘要**

   每条摘要记录来源消息范围、生成版本、不可丢失的约束和未知项；摘要失效时能回退到原消息。

2. **增加受控情景记忆**

   在明确需求成立后增加自由文本或结构化情景记忆，但继续沿用来源、确认、revision、TTL、冲突和删除机制；向量只做候选索引，PostgreSQL 继续作为权威状态。

3. **统一上下文计划**

   将对话和证据上下文统一到可审计的 `ContextPlan`，记录每个片段的包含、压缩、裁剪和拒绝原因。

4. **使用模型相关的 token 预算**

   在保留安全字节上限的同时，增加实际 tokenizer 预算和模型窗口适配。

5. **补充记忆安全评测**

   建立专门的 Badcase 集：过期偏好、错误偏好、提示注入、跨用户泄漏、摘要丢失、删除传播和权限收回。

6. **保留负结果**

   没有可重复证据的质量收益，不进入默认上下文策略；不让“更多记忆”自动等同于“更好回答”。
