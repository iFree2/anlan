# 安澜：作业前、作业中、作业后的新手演示脚本

适用日期：2026-10-26。依据当前P12双角色实现、已交付演示与代码核对编写；不是新增功能开发或真实安全作业规程。本次编写没有运行新申请、触发供应商模型、修改云端配置。

## 1. 先说结论：原设想尚不完全满足

目前最准确的定位是：**双角色材料核查协作 + 合成事件的事实/知识辅助核查 + 可追溯记录与人工反馈**，不是完整作业许可、实时监控和销票系统。

| 你希望演示的内容 | 当前是否满足 | 演示时怎样表述 |
|---|---|---|
| 申请人一句话说明对象、方式、位置 | 已实现 | 模型提取材料，先出确认卡片，再创建任务 |
| 生成正式申请 | 部分实现 | 生成结构化材料申请，不是法定/企业正式动火作业票；当前核心材料仅位置、对象、方式、附件说明 |
| 交给另一名安全人员核查 | 已实现 | 不同身份、独立会话，共享同一个申请编号 |
| 审核中要求补充材料并重提 | 已实现 | 安全人员提出具体问题，申请人补充原任务、重新提交 |
| 审核前发现资质/区域/制度未取到，自动调工具补齐 | 尚未接入该业务阶段 | 查询能力存在，但当前网页主链在“事件核查”时调用；不是审批前的独立证据预核查 |
| 外部系统或知识库根本没有数据，Agent补出真实资料 | 不满足，不能编造 | 已有数据可查询；缺失、过期或无权必须保留unknown/error，交人工/数据维护，不等于查不合格 |
| 依据全部补齐后正式审批、允许开工 | 未实现 | 只能演示“人工材料核查完成”，不能说批准或开工授权 |
| 工人实际进入指定区域、自动关联人员/位置 | 未实现 | 没有真实门禁/定位/作业人员动态绑定闭环 |
| 从视频平台、气体平台实时订阅/消费告警 | 外部平台尚未接入 | 有事件接收/关联/核查后端合同，当前网页通过合成按钮生成事件；不是实时摄像头识别或传感器采集 |
| 未戴安全帽、气体异常两类事件核查 | 已实现，合成输入 | 安全人员点“核查所选事件”，工具读取事实/知识，再由模型给受约束候选 |
| 任意事件发生后自动后台研判、推送安全人员 | 不完整 | 已有协作待办/收件箱与页面轮询，但当前核查由安全人员手动触发；没有自动告警派单/短信/IM推送 |
| 给出判断和处理建议 | 部分实现 | 页面显示关注项和工具结果状态；接口有受限next_steps，不是自由处置方案/控制指令 |
| 人工选择反馈 | 已实现 | 需要继续核实/确认事件/对事件有异议；不是处置工单或报警关闭 |
| 作业后复盘 | 可做记录回看与人工复盘 | 有材料版本、业务时间线、事件、依据和反馈；无自动完工验收、销票或一键复盘报告 |

### “补充”必须分清三种情况

1. **材料没写清楚**：例如具体工位不明。请申请人补充，当前已实现。
2. **系统已有资料，但还没查**：查询已有资质记录、区域状态，检索已有知识。当前网页在事件核查中实现。
3. **源系统根本没资料**：不能靠模型生成证书、补造制度或假设条件合格。当前不会替源系统维护真实资料。

另一个边界：工具链是宿主编排的固定事实/知识分支，并非模型任意发现和调用企业MCP。自然语言里的任意姓名、位置，也不会自动变成已验证的人员ID/区域ID。

## 2. 本次真正能演练的主线

**一句话申请 → 确认创建 → 提交指定安全人员 → 要求补充 → 原申请更新/重提 → 人工材料核查完成 → 明示外部审批缺口 → 手动模拟两种事件 → 调工具/知识辅助核查 → 人工反馈 → 回看记录并人工复盘。**

预计15—20分钟，建议第一次不要一边改提示词一边演示。所有业务都是SYNTHETIC合成样例，不进行真实动火作业。

### 三项查询究竟什么时候触发？

**当前网页的明确触发点是：安全人员选择一条合法、当前可核查的事件，然后点击“核查所选事件”。** 通过身份、事件关联和材料版本等检查后，系统发起人员资质、区域状态、规程知识三项查询，再把结果交给模型综合。不是模型先判断“资料缺少”，才临时决定查哪一个工具。

| 演示者的动作 | 是否发起这三项查询 | 实际发生什么 |
|---|---|---|
| 申请人发送一句话申请 | 不会 | 意图识别，生成待确认材料候选 |
| 确认创建、补充材料 | 不会 | 创建/更新材料，执行材料分析，不是三工具事实核查 |
| 提交申请、要求补充、重提、材料核查完成 | 不会 | 执行协作状态变化、记录及通知；不是自动查询资质/规程的开关 |
| 在聊天里说“帮我查资质、位置、制度” | 不是当前已实现的三工具触发入口 | 不能把聊天回复当成实际查询证明 |
| 点击“＋ 未戴安全帽”或“＋ 气体浓度异常” | 仅生成事件，不会 | 保存合成事件并显示记录；尚未进行三项依据核查 |
| 选择事件后点击“核查所选事件” | **会，正常核查入口** | 合法性检查→发起三项只读查询→汇总依据→模型生成受约束候选→保存核查 |
| 选择已完成核查、刷新页面、查看反馈 | 不会重新查询 | 读取已有核查/状态；不等于重新执行工具或模型 |
| 再次点击“核查所选事件” | 新核查请求会重新发起 | 不是单纯刷新，可能再次消费模型费用；不要为了看结果重复点击 |

“发起三项查询”不保证三项都成功。无权限、过时事件或材料冲突可能在采集前拒绝；查询中的缺失、错误、超时或取消也应如实保留，不能把“触发过”讲成“查证成功”。

### 具体查谁、查哪个位置、查哪些规程？

| 查询 | 当前参数/来源 | 能查到什么，不代表什么 |
|---|---|---|
| 人员资质 `query_worker_qualification` | 服务器可信演示配置中的worker_id、qualification_type；本套样例为worker-p5-001和welding | 查询既有资质记录及其状态/有效性，不是根据申请账号自动确认真实作业人员，也不生成缺失证书 |
| “位置查询”实际为区域状态 `query_area_status` | 服务器配置的area_id；本套样例为area-p5-demo，并与事件可信绑定核对 | 查询预设区域状态；不是地图搜索、GPS/视频定位，也没有自动验证申请文本里的“东侧2号工位”就是该区域 |
| 规程知识 `query_knowledge` | 事件类型生成的固定示例问题，加当前租户/读者/有效性范围 | 检索已入库的合成制度/规程，返回可用内容与引用或未知；不会替缺失知识库补写真实制度 |

例如，安全帽事件使用“未戴安全帽事件需核对哪些示例依据？”这类固定问题；气体事件使用对应的气体异常示例问题。并不是把聊天里任意一句话都自动送到这个知识检索入口。

内部顺序也不是“三个模型挨个聊天”：**事实分支先查资质、再查区域；知识分支与事实分支并行检索；汇合后再由模型综合。** 页面按o1/o2/o3展示结果编号，不代表三者都顺序执行。

### 在演示中怎样把触发点讲清楚

在步骤7分两次停顿，不要把生成事件和核查合成一个动作：

1. 点“＋ 未戴安全帽”后停顿：**“现在只是模拟平台送来一条事件，还没有查询资质、区域和制度。”**
2. 点“核查所选事件”前说明：**“这一步才启动三项依据查询。人员和区域来自服务器预设的合成引用，知识来自已准备的示例库。”**
3. 结果返回后指向三行依据：**“这里分别是资质、区域状态和知识查询的结果；ok只表示查询成功，未知项仍要人工核实。”**
4. 再说明：**“Agent在这些依据之上生成关注项和受限建议，不补造资料，不自动审批，也不控制报警。”**

若想在“审核期间”展示这套查询，已分配安全人员也可在待核查阶段，对合法且当前的合成事件点击相同入口；它并不要求申请先变成“材料核查完成”。但这仍然是**事件核查工具链**，不是已实现了审批前自动预核查。主线将其放在第二幕，是为了避免混淆业务阶段。

## 4. 第一幕：作业前——申请、补充与材料核查

### 步骤1：申请人用一句话发起

窗口A发送：

> 我要申请动火作业：在合成园区检修区A工位，对演示试件A的焊缝采用电弧焊进行补焊；附件说明为试件A的位置示意图和焊缝照片说明，本轮全部为SYNTHETIC合成演示。

观察：应先出现待确认卡片，列出位置、对象、方式、附件说明。**看到卡片还不等于已创建申请。**

操作：核对后点击卡片“确认”。等待分析完成，右侧出现材料任务和申请编号，记为“申请X”。若模型追问某项，按问题补充，不要求它忽略缺项。

说明：当前附件字段是文本说明，本步骤没有真的上传照片，不要讲成“Agent已经看过照片内容”。材料分析完成也不是审批完成。

### 步骤2：申请人主动提交给安全人员

窗口A右侧“提交给安全人员”选择 `safety-manager-demo`，点击 **“提交给安全人员（先确认）”**。

观察确认卡片中的申请X、材料版本和核查人，再点击“确认”。

预期：共享申请由草稿进入“待安全人员核查”。不要仅在聊天中说“已经提交了”，以右侧状态和共享业务时间线为准。

讲解：

> 材料准备好和正式交给对方核对，是两个动作。重要操作都要本人二次确认。

### 步骤3：安全人员在自己的窗口打开同一申请

窗口B左侧“分配给我的待办”找到申请X并点击；必要时点“刷新”，等页面轮询更新。

检查：两端申请编号相同；安全人员看到共享材料和业务进展，不会得到申请人的全部私人聊天。

此处必须声明原设想的缺口：

> 现在如果要在正式审批前自动查询人员资质、区域条件和制度依据，这一业务接入还没有完成。本轮先演示已实现的材料补充协作；工具查询能力将在后面的事件核查中展示。不能用“请查资质”一句闲聊，冒充系统真的完成了预审查询。

### 步骤4：安全人员要求位置更具体

窗口B右侧“提出补充要求”的文本框填写：

> 请把作业位置补充到检修区东侧2号工位，并说明演示试件A的具体摆放点，便于核对本轮申请。

点击 **“提出补充要求（先确认）”**，检查卡片后“确认”。

预期：共享申请变为“待申请人补充”；窗口A收到同一项具体补充要求。这里是安全人员人工提出的问题，不要讲成模型已经发现了真实现场问题。

### 步骤5：申请人在原申请中补充，不另建任务

回到窗口A，确认仍为申请X，在聊天中发送：

> 补充作业位置：合成园区检修区东侧2号工位，演示试件A摆放在该工位中心工作台上。其余作业对象、作业方式和附件说明保持不变，全部为合成演示。

等待右侧材料更新。观察申请编号仍为X，材料版本递增；如有新确认卡片先核对再确认。**不要点“发起另一项”，也不要说“重新申请一个”。**

随后在“重新提交申请”的说明框填写：

> 已补充东侧2号工位和试件摆放点，请核对本轮最新材料。

点击 **“重新提交申请（先确认）”**，再确认。补材料和重新提交仍是两个动作。

### 步骤6：安全人员完成人工材料核查

窗口B刷新申请X，核对本轮位置和最新提交版本。在“完成人工材料核查”的说明框填写：

> 已人工核对本轮位置、对象、方式和附件说明，材料核查完成。本记录仅表示材料核对，不代表正式作业批准或开工授权。

点击 **“完成人工材料核查（先确认）”**，再确认。

预期：双方都显示“材料核查完成”，共享时间线保留提交、补充要求、重提和完成记录。

这里不能说“工人已经通过审批，可以开始动火”。也不要继续修改这份已完成材料；当前完成状态会冻结材料编辑。

## 5. 第二幕：作业中——合成事件、工具依据与人工反馈

### 先做一段明确的场景切换

讲解：

> 下面只是假设场景进入了作业中。正式审批、开工许可、人员真实到场和区域准入不由当前Agent完成，也不表示我们真的完成过这些动作。接下来用按钮模拟外部平台送来事件，演示接收后的辅助核查链路。

### 步骤7：模拟未戴安全帽事件

保持窗口B、申请X，展开右侧 **“事件、核查与反馈详情”**。

点击 **“＋ 未戴安全帽”**。选择新生成的事件，点击 **“核查所选事件”**，等待结果。

这两个点击含义不同：前一个生成合成事件；后一个才发起依据收集和模型核查。没有摄像头视频输入，不能讲成安澜自行识别了某个人。

按第2节“三项查询究竟什么时候触发”的四句讲解，在两个点击之间停顿。此处就是本演示展示资质查询、区域状态查询和规程知识检索的主要位置；不要提前在“确认提交申请”时宣布它们已完成。

实际工具链会查询：

| 依据标识 | 工具名 | 含义 |
|---|---|---|
| o1 | query_worker_qualification | 查询服务器预设合成人员的资质记录 |
| o2 | query_area_status | 查询服务器预设合成区域的状态 |
| o3 | query_knowledge | 检索已存在的合成制度/规程知识 |
| e1 | 原始事件 | 本次合成未戴安全帽事件，不是工具观察 |

页面主要展示关注项和各工具的ok/unknown/error。**ok表示本次查询取得符合工具合同的结果，不等于作业安全，也不是审批通过。** 查不到时应如实保留证据缺口，不能现场编造查询结果。

讲解：

> 安澜不是只看见一个报警就给结论。它把报警、资质记录、区域状态和知识依据放在一起，生成受约束的关注项；真正的现场核实和处置仍由安全人员负责。

### 步骤8：区分候选建议与页面展示

当前页面可能出现的关注项：

- `helmet_missing`：本条未戴安全帽事件需要关注。
- `evidence_gap`：有依据未知或不可用，需要继续核实。
- `context_for_review`：有知识依据可供人工复核。

接口中的 `next_steps` 是受限枚举，核心为 `verify_event_on_site`（到现场核实事件）、`review_evidence_with_safety_manager`（由安全人员复核依据）；在材料缺项状态下还可能有 `complete_material`。不是模型任意生成停工、复工或报警控制指令。

**当前页面没有把next_steps或全部知识原文引用展开渲染。** 不要在脚本中声称页面已有一段完整处置建议。需要展示接口细节时用附录A的只读方法；讲解员翻译上述枚举时应说明这是接口含义，不是页面新增文本。

### 步骤9：安全人员记录人工反馈

在“安全管理人员反馈”下拉框选择 **“需要继续核实”**，点击 **“保存人工反馈”**。

预期：反馈已保存，原始报警仍为 `active`。这里没有处理工单、整改说明自由文本或“关闭报警”按钮。

如演练中有真实依据支持对某个合成事件标签的人工认可，也可演示“确认事件”；它只表示确认事件，不是确认风险已消除。没有核实就保持“需要继续核实”。

### 步骤10：模拟气体浓度异常

仍在窗口B、申请X，点击 **“＋ 气体浓度异常”**，选择新事件，再点 **“核查所选事件”**。

观察：本条类型为 `gas_abnormal`；工具仍按本次事件上下文收集合成事实/知识，再由模型综合。为本条单独保存“需要继续核实”反馈，避免把上一条反馈当成本条。

当前按钮产生的是预置合成异常记录，不是传感器连续采样。即使接口里看到数值/单位，也不是现场测量、当前合规阈值或开工作业依据；不要把示例数值当成规范阈值。

讲解：

> 安全人员现在掌握了两条事件及其核查依据。下一步采取什么现场处理机制，由企业制度和人工判断决定，当前Agent不执行现场控制，也不确认恢复作业。

### 这段演示不能称为“自动推送”

安全人员已在自己的待办页面里主动发起核查。当前有页面轮询和协作通知，但没有演示后台实时告警订阅、自动判定后分派、短信或IM通知。共享时间线出现核查/反馈记录，也不能冒充告警平台自动派单。

## 6. 第三幕：作业后——回看、反馈与人工复盘

### 这一步的业务价值

不是再让Agent批准一次，而是回答：**申请发生了什么变化、出现了哪些事件、当时查到了什么依据、哪些仍未知、人工留下了什么意见。** 当前可回看这些记录，但没有正式完工/销票状态。

### 步骤11：回看本次申请和核查记录

1. 窗口B打开申请X的 **“共享业务时间线”**，按实际记录回看提交、要求补充、重提和材料核查完成。
2. 展开 **“事件、核查与反馈详情”**，分别选择两条事件，查看核查状态、依据结果和人工反馈。
3. 确认记录仍属于申请X；不要把其他会话里的旧事件混入本轮复盘。
4. 查看核查是否仍“当前有效”。过期、材料已变化或被新事件取代的结果，只能作为历史，不能当最新依据。当前云端固定回放时钟，不把此处时间标签当成真实现场有效性证明。
5. 原始报警可能仍为active，因为当前Agent不负责清警。没有外部处置证据就不能总结成“风险已解除”。

### 步骤12：安全人员作人工复盘，演示者整理一页记录

讲解：

> 这次复盘的价值在于可追溯。我们可以看到材料如何补齐、事件如何核查、哪些依据支持了候选、人工是否反馈。当前还没有一键生成本次作业总结，所以这一页由演示人员根据记录整理，不能说成Agent已经自动完成。

复制下面模板到自己的笔记，按屏幕实际结果填写。**模板不是当前产品功能，也不写入Agent后台。**

```text
演示申请编号：
数据性质：SYNTHETIC合成演示
材料：首次版本___，最终版本___；是否有补充/重提___
材料核查：核查人___；本轮人工说明___
事件：未戴安全帽___条；气体异常___条（按实际生成数量）
核查：成功___条；失败/取消___条；已过时___条
依据：资质___；区域___；知识___（填写实际ok/unknown/error）
人工反馈：需要继续核实___；确认事件___；有异议___
未解决事项：
外部处置：有独立记录则引用；没有就写“本系统未记录/未验证”
改进建议：例如材料首次写到具体工位，缺失源数据由维护人员补齐
边界：材料核查完成不等于作业批准；反馈不等于报警关闭
```

这里不能让申请人在完成状态下“补一个作业结束说明”，冒充既有完工流程。聊天里说“已经完工”，也不会自动生成可信完工验收或销票记录。

## 7. 可选加演：旧核查为什么不能跟着材料自动生效

主线已经完成材料核查，不要强行改已冻结材料。若想加演这一能力，用**另一份新申请**：

1. 提交给安全人员，保持待核查。
2. 生成一条合成事件并完成核查，观察当前版本。
3. 安全人员要求补充位置，申请人更新材料，再重新提交。
4. 安全人员查看旧核查，确认其标记“材料已变化”/`stale_material`；原报警和反馈保留。

这段是已实现的版本有效性演示，不证明真实作业阶段变更或外部监控接入。会多产生模型调用，不必第一次演练就做。

## 8. 附录A：查看已有核查接口里的建议和知识引用

仅供希望看清Agent内部链路的演练者，不需要写代码或重新调模型。

1. 在安全人员窗口按F12，切到Network/网络，选择Fetch/XHR筛选。
2. 保持面板打开，回页面选择一条**已有且已完成**的事件核查。只选记录，不点“核查所选事件”。
3. 找到形如 `GET /anlan/reviews/某个review_id` 的请求，不是列表或POST核查请求。
4. 在Preview/预览或Response/响应中展开 `result.report`。
5. `candidate.concerns` 是关注项；`candidate.next_steps` 是受限后续建议；`observations` 是三项工具结果。
6. 在工具名为 `query_knowledge` 的观察中查看 `citations`（若有），核对原文摘录、文档/片段标识和版本。找不到引用时记录缺口，不虚构引用。

只看响应，不复制/录制Request Headers里的Authorization，不展示访问配置内容。不把某条引用存在等同于全部模型结论已获充分支持。

## 9. 附录B：开发者已经具备的离线质量回放

已有质量CLI可以查看、重验**冻结学习案例**，不新调工具/模型，也不自动导入刚才的申请X。它是“改进Agent可靠性”的开发者功能，不是“这份作业自动生成复盘报告”。

在项目根目录PowerShell执行：

```powershell
.venv/Scripts/python.exe -m anlan.interfaces.quality_cli inspect --manifest evals/quality-v1/manifest.json --output .runtime/post-work-inspect-20261026-01.json
.venv/Scripts/python.exe -m anlan.interfaces.quality_cli replay --manifest evals/quality-v1/manifest.json --split dev --output .runtime/post-work-replay-20261026-01.json
```

文件名存在时换新后缀，不覆盖。inspect查看已有证据，replay只重新验证已记录候选，不重新执行现场工具。报告中的不可回放案例、失败和小样本限制应保留；不是模型泛化率、自动学习生效或现场安全成效。

不要把“给Agent点赞”“保存反馈”讲成它已经自动更新模型、自动写入知识库，当前没有这个闭环。

## 10. 演练验收与常见卡点

- 两个窗口的可信角色不同，任务编号相同。
- 有一次完整的提交→补充要求→原任务更新→重提→人工材料核查完成。
- 两类事件均手动合成、分别核查和记录反馈；失败时如实说明，不以旁白替代返回。
- 能解释o1/o2/o3是查询，不是编造缺失资料；next_steps不是自动现场控制。
- 能回看人工记录，区分材料完成、事件反馈、报警状态和正式作业状态。
- 能明确说出尚缺预审证据接入、正式许可、真实订阅/自动推送、自动完工/销票及报告。

| 卡点 | 先检查什么 |
|---|---|
| 安全人员看不到申请 | 申请人是否真正确认提交、是否选对核查人、两端是否同租户并刷新 |
| 输入了“确认”，仍未提交 | 是否有真实待确认卡片、处理是否失败、右侧状态是否变化；不要重复点或另建申请掩盖问题 |
| 仍提示发送保存但处理失败 | 历史失败不会被删除；新失败仍可能来自格式/网络等原因，取消项目限额不等于所有故障已修复 |
| 有告警但没核查结果 | 生成事件与核查是两个动作；检查是否点了“核查所选事件” |
| 某项依据unknown/error | 如实解释来源缺口/不可用，不说核查通过；不要自动补造资料 |
| 看不到建议/引用全文 | 当前UI只显示部分结果，用附录A查看已有响应，不把聊天回复当正式核查报告 |
| 气体事件反馈看起来不对 | 是否选中了正确事件及其对应核查，而不是上一条安全帽事件 |
| 页面仍显示报警active | 正常边界：本Agent没有清警能力，反馈不控制报警 |

依据：P12验收/交接/部署；`collaboration/policy.py`、`interfaces/console/service.py`、`interfaces/perception_runtime.py`、`workflows/parallel.py`、`workflows/perception_contracts.py`、console assets及quality CLI。没有为本脚本新增或重新部署业务能力。
