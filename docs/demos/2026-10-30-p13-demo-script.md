# 安澜 2.0 P13 演示脚本

日期：2026-10-30

演示时长：12—15 分钟

演示目标：两个不同身份围绕同一份动火申请，完成“异常依据被阻断 → 安全人员要求补充 → 申请人换绑定并重提 → 安全人员确认引用并完成材料核查 → 合成事件复核”的闭环。

> 全部数据均为 SYNTHETIC 合成数据。材料核查完成不等于正式审批、作业许可或开工授权。原始报警由外部系统管理，安澜不自动清警或控制现场。

## 一、演示前准备

### 1. 启动本地服务

在项目根目录打开第一个 PowerShell 窗口：

```powershell
Set-Location 'D:\src\agent学习\安澜2.0'
. .\scripts\dev-postgres.ps1 -Action Start
. .\scripts\dev-postgres.ps1 -Action Env
$env:ANLAN_DATABASE_URL = $env:ANLAN_DATABASE_URL -replace '/anlan_dev$', '/anlan_p13_b3_check_20261028'
.\.venv\Scripts\python.exe -m anlan.interfaces.serve `
  --config .runtime\p13-b3-browser-demo-2\service.json `
  --port 8017
```

看到服务持续运行即可。这个窗口不要关闭。

如果本机已有旧服务占用 `8017`，先关闭旧服务；不要同时启动两个使用同一数据库的演示实例。

### 2. 打开两个独立浏览器窗口

两个窗口都打开：

```text
http://127.0.0.1:8017/console
```

窗口 A 选择：

```text
D:\src\agent学习\安澜2.0\.runtime\p13-b3-browser-demo-2\applicant.json
```

窗口 B 选择：

```text
D:\src\agent学习\安澜2.0\.runtime\p13-b3-browser-demo-2\safety-manager.json
```

选择文件后页面会自动连接。预期页头分别为：

- 窗口 A：`申请人（演示身份）`
- 窗口 B：`安全人员（演示身份）`

如果不是两个不同身份，立即断开并重新选择配置。不要把配置文件内容、令牌或数据库连接串放进截图、录屏和聊天。

### 3. 开始前的口述

> 这里使用两名不同身份的独立会话。两个人共享同一份申请、材料版本和证据，但彼此看不到私聊。全程是合成数据，系统终点是“材料核查完成”，不是审批通过或允许开工。

## 二、正式演示

### 第 1 步：申请人创建一个资质异常申请

在窗口 A：

1. 点击左上角 `＋` 新建会话。
2. 在聊天框粘贴：

```text
申请动火，作业位置在合成受限区域，作业对象是合成异常试件，作业方式是焊接演示，附件是合成附件
```

3. 发送后等待“请确认安澜的理解”卡片。

预期效果：

- 卡片显示作业位置、作业对象、作业方式、附件说明；
- 此时申请还没有创建；
- 卡片上只有确认后才会写入申请。

操作：核对四项，点击 `确认申请`。

讲稿：

> 模型负责把自然语言整理成结构化材料，但不会未经确认直接创建申请。看到确认卡片不等于任务已经建立。

### 第 2 步：申请人选择异常对象并确认绑定

在右侧“作业前依据”区域：

1. 作业人员选择 `SYNTHETIC 资质异常人员`；
2. 资质类型选择 `SYNTHETIC 焊接资质`；
3. 作业区域选择 `SYNTHETIC 受限区域`；
4. 点击 `确认本申请对象`。

预期效果：

- 右侧出现申请编号，记作“申请 X”；
- 材料版本为 `v1`；
- 绑定版本为 `v1`；
- 页面显示 `worker-p13-alert` 和 `area-p13-restricted`；
- 此时尚未查询依据，状态会先显示“待核查”或“核查排队中”。

讲稿：

> 人员和区域必须从服务端授权目录明确选择。申请账号不是作业人员，系统也不会因为材料里写了“合成受限区域”就静默猜出一个可信区域 ID。

### 第 3 步：申请人提交给安全人员

在窗口 A 聊天框发送：

```text
提交申请给 safety-manager-demo
```

出现确认卡片后检查：

- 申请编号是刚才的申请 X；
- 申请人身份是 `applicant-demo`；
- 安全人员是 `safety-manager-demo`；
- 材料版本为 `v1`；
- 绑定版本为 `v1`。

点击 `确认`。

预期效果：

- 申请状态变为 `待安全人员核查 / under_review`；
- 系统自动启动资质、区域和知识三项只读查询；
- 几秒后状态从“核查中”变为 `依据有缺口`。

讲稿：

> 提交和重提后，系统会把三条依据查询作为持久化任务启动。刷新页面或重复确认不会重复创建查询任务。

### 第 4 步：安全人员打开同一申请

切换到窗口 B：

1. 点击左上角 `＋` 新建会话；
2. 在“分配给我的待办”中找到刚创建的申请 X；
3. 点击该申请，必要时点 `刷新`。

预期效果：

- 两端申请编号完全相同；
- 安全人员看到共享材料，但看不到申请人的私聊；
- 当前状态显示 `依据有缺口 · 当前`；
- 人员资质显示 `查询 ok · 业务状态 suspended`；
- 区域状态显示 `查询 ok · 业务状态 restricted`；
- 缺口明确列出 `worker_not_current_active` 和 `area_not_current_normal`；
- 页面没有可以绕过缺口的材料完成入口。

讲稿：

> 查询成功不等于业务通过。这里资质和区域都成功查到了记录，但业务状态分别是暂停和受限，所以材料完成被阻断。这正是“查到结果”和“满足完成条件”的区别。

### 第 5 步：安全人员提出补充要求

在窗口 B 的“提出补充要求”文本框填写：

```text
请改用资质有效人员和正常作业区域后重新提交。
```

点击 `提出补充要求（先确认）`，检查确认卡片后点击 `确认`。

预期效果：

- 申请状态变为 `待申请人补充 / changes_requested`；
- 窗口 A 的共享业务时间线出现“要求补充”；
- 补充要求内容完整可见；
- 原依据仍保留用于历史查看，但不能作为完成依据。

讲稿：

> 缺口不会阻止安全人员说明问题或申请人补充。完成条件被阻断，但处理路径保持畅通。

### 第 6 步：申请人换人员、换区域并确认

切换回窗口 A，点击 `刷新`。

预期先看到：

- 状态为 `待申请人补充`；
- 旧依据显示 `依据已过时 · 非当前`；
- 绑定仍然显示异常人员和受限区域；
- 右侧出现新的对象选择表单，默认值为空。

依次选择：

1. `SYNTHETIC 正常作业人员`；
2. `SYNTHETIC 焊接资质`；
3. `SYNTHETIC 正常区域`；
4. 点击 `确认本申请对象`。

预期效果：

- 绑定版本从 `v1` 变为 `v2`；
- 页面显示 `worker-p13-normal` 和 `area-p13-normal`；
- 旧依据继续显示过时；
- 此时还没有新依据，因为申请尚未重提。

讲稿：

> 换人换区域必须产生新的绑定版本。只改绑定也必须允许重提，不需要为了制造版本号去修改无关材料文字。

### 第 7 步：申请人在原申请中重提

在窗口 A 的“重新提交申请”文本框填写：

```text
已换为资质有效人员和正常作业区域，请重新核查。
```

点击 `重新提交申请（先确认）`。

检查确认卡片：

- 仍是同一个申请 X；
- 材料版本仍为 `v1`；
- 绑定版本为 `v2`；
- 没有新建另一项申请。

点击 `确认`。

预期效果：

- 申请返回 `待安全人员核查`；
- 系统为新的绑定版本自动创建新预核查；
- 几秒后依据从“核查中”变为 `依据可供人工核对 · 当前`。

讲稿：

> 材料没有变化，但绑定发生了实质变化，所以合法重提并生成新的依据批次。旧批次不会覆盖新批次。

### 第 8 步：安全人员核对新的当前依据

切换窗口 B，点击 `刷新`。

预期效果：

- 绑定版本为 `v2`；
- 人员显示 `SYNTHETIC 正常作业人员 / worker-p13-normal`；
- 区域显示 `SYNTHETIC 正常区域 / area-p13-normal`；
- 人员业务状态为 `active`；
- 区域业务状态为 `normal`；
- 查询时间显示固定合成时间 `2026-09-22T04:00:00Z`，即北京时间 `12:00`；
- 有效至显示 `2026-09-22T04:10:00`；
- 知识候选显示来源、版本和摘要；
- 页面出现知识引用勾选和“人工适用性结论”输入框。

讲稿：

> 页面同时展示实际查询时刻、来源观察时间和来源有效期。固定时钟只用于重复演示，不能当成真实现场时间的可靠性证明。

### 第 9 步：安全人员人工选择本轮引用

在窗口 B：

1. 勾选与上方摘录“作业前先核对已确认作业人员的焊接资质、当前区域状态和适用规程”对应的那一条引用；
2. 在人工结论中填写：

```text
已人工确认正常人员、正常区域和动火前置规程引用适用于本轮材料核查。
```

3. 点击 `冻结采用引用并确认`。

出现“材料核查完成”确认卡片后，检查：

- 申请版本；
- 材料版本 `v1`；
- 绑定版本 `v2`；
- 预核查 check ID；
- 人工采用的引用 ID；
- 人工结论。

确认无误后点击 `确认`。

预期效果：

- 申请状态变为 `材料核查完成 / review_completed`；
- 共享时间线显示：提交申请 → 要求补充 → 重新提交 → 材料核查完成；
- 完成记录绑定当前 check 和绑定 v2；
- 页面仍明确显示“材料核查完成≠批准作业”。

讲稿：

> 系统不会让模型替人选择规程，也不会接受任意引用 ID。安全人员明确选择本轮适用引用后，服务端再检查当前性、来源权限、有效期和完成门控。

## 三、作业中事件复核

### 第 10 步：安全人员生成合成气体事件

仍在窗口 B：

1. 展开“事件、核查与反馈详情”；
2. 点击 `＋ 气体浓度异常`；
3. 等待页面提示“合成事件已保存；原始报警保持 active”；
4. 点击刚生成的事件；
5. 点击 `核查所选事件`。

预期效果：

- 事件类型显示“气体浓度异常”；
- 原始报警保持 `active`；
- 事件属于当前申请；结合上方的“作业前依据”卡片，可以核对当前申请对象是 `area-p13-normal`；
- 核查状态显示“核查完成 · 当前有效”；
- 三项依据分别显示 `query_worker_qualification · ok`、`query_area_status · ok`、`query_knowledge · ok`。

说明：当前页面的事件条目主要显示“材料 v1”，不会直接展开区域 ID；区域是否属于本申请对象，以“作业前依据”卡片和服务端绑定校验为准。

讲稿：

> 这里的事件来源是页面合成的，不是真实视频或气体平台。系统展示的是事件进入后的依据复核链路；助理不会自动关闭报警，也不会控制现场。

### 第 11 步：保存人工反馈

在“安全管理人员反馈”中选择：

```text
需要继续核实
```

点击 `保存人工反馈`。

预期效果：

- 页面显示反馈已保存；
- 原始报警仍为 `active`；
- 事件核查记录仍为当前有效；
- 不会生成正式处置单，也不会改变材料核查状态。

讲稿：

> 人工反馈记录的是人的判断，不是系统处置结论。“确认事件”也只表示确认事件存在，不代表风险已经解除。

## 四、收尾演示

切换两个窗口，指出：

1. 两边使用同一申请编号；
2. 材料版本始终为 `v1`，但绑定从 `v1` 升到了 `v2`；
3. 旧异常依据没有被删除，而是被标为历史；
4. 当前完成记录使用新绑定、新 check 和人工选择的引用；
5. 事件复核使用当前申请对象；
6. 原始报警保持 `active`；
7. 页面没有出现“已批准”“允许开工”或“自动销票”。

最后说：

> 本次展示的是一条可追溯的作业前材料核查和作业中事件复核链路。系统把对象、版本、来源、时间、缺口和人工选择都保留下来，避免把查询成功误当安全通过，也避免把材料核查完成讲成正式许可。

## 五、必须记住的六句话

| 可以说 | 不能说 |
|---|---|
| 提交后自动执行三项只读查询 | 查询成功就说明作业安全 |
| 资质暂停和区域受限会阻断完成 | Agent 自动查明了事故原因 |
| 换人换区域会生成新绑定版本 | 修改材料版本才能重提 |
| 安全人员明确选择本轮知识引用 | 模型替人选中了适用规程 |
| 事件依据来自当前申请绑定 | 页面正在连接真实视频或气体平台 |
| 材料核查完成并保留完整历史 | 系统已正式批准、允许开工或销票 |

## 六、常见问题

### 看不到安全人员的完成表单

依次检查：

1. 当前是否为 `safety_manager` 身份；
2. 申请是否处于 `under_review`；
3. 预核查是否为 `ready` 且 `current=true`；
4. 是否存在有效知识引用；
5. 是否先通过右侧结构化表单选择引用，而不是只在聊天里说“确认”。

### 重提后仍显示旧依据

刷新页面并等待自动查询完成。如果一直不更新，检查：

- 材料、绑定和申请版本是否与确认卡片一致；
- 新查询是否处于 `queued`、`running` 或 `failed`；
- 不要编辑无关文字伪造新版本。

### 事件提示 409

通常是事件生成后申请绑定又发生了变化。按当前绑定重新生成事件；旧事件保留历史，但不能再用于当前核查。

### 页面显示 `unknown` 或 `error`

如实说明来源缺口，不要改口为“核查通过”。先检查事实/知识来源、有效期、租户和读者权限，再由授权人员修复来源并显式重查。

## 七、演示成功标准

- [ ] 两个隔离窗口使用不同身份；
- [ ] 两端显示同一申请编号；
- [ ] 初始异常为 `suspended` 和 `restricted`，完成被阻断；
- [ ] 安全人员提出补充要求，申请人换绑定并重提；
- [ ] 材料版本不变、绑定版本增加，旧依据变为历史；
- [ ] 安全人员人工选择引用并完成材料核查；
- [ ] 完成状态明确显示不等于审批或开工；
- [ ] 合成事件使用当前申请区域，原始报警保持 `active`；
- [ ] 全程没有展示令牌、连接串或真实企业资料。

## 附：从空环境重新准备演示数据

只有现有 `.runtime\p13-b3-browser-demo-2` 不可用时才执行：

```powershell
.\.venv\Scripts\python.exe scripts\prepare_collaboration_demo.py `
  --output .runtime\p13-demo-20261030
```

随后按新目录 `service.json` 的租户和两名用户，向本地知识库导入公开合成知识。演示时让后端使用新的 `service.json`，两个浏览器分别选择该目录下的 `applicant.json` 和 `safety-manager.json`。

知识导入必须保留两名角色都可读取的 `allowed_users`，否则预核查会正确显示知识缺口，无法演示 ready 路径。
