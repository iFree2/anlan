# 安澜 2.0：作业前 / 作业中 / 作业后 三幕演示脚本（可演练版）

适用日期：2026-10-28。本页面向第一次接触安澜的人，目标是**照着做就能跑通一遍，并且知道哪些话能说、哪些不能说**。

编写依据：本页的事实来自三类可复核来源——(1) 仓库内已交付的实现与文档；(2) 本轮在本机实际执行的命令与接口调用（见第 6 节"本轮实测证据"）；(3) 云端线上实际返回的接口数据。本轮**没有**为了写脚本而触发真实模型调用、没有改业务代码、没有部署。

## 0. 先给结论

你设想的三段场景，落在当前交付上的真实情况是：**作业前"两人协作 + 材料补充重提"能完整演；作业中只能演"合成事件到达后的依据核查"，没有真实视频/气体平台订阅与自动推送；作业后只有"回看记录 + 人工复盘 + 离线质量回放"，没有一键复盘报告、没有完工/销票。**

| 你设想的能力 | 当前状态 | 一句话真相 |
|---|---|---|
| 申请人一句话 → 结构化材料 → 交安全人员 | ✅ 已实现（云端可演） | DeepSeek 抽取四项材料，先出确认卡片，确认后才建任务 |

因此本脚本的演示主线是：**能演的演足，不能演的当场说清**。这比含糊盖过去更能体现你对系统的理解。

## 1. 三幕演示主线（推荐路线：云端，20—25 分钟）

### 1.1 为什么推荐云端

- 零安装：只要浏览器 + 仓库里已有的两份私密访问配置。
- 真实模型：材料分析、事件核查走 DeepSeek（`deepseek-flash`），能讲清"模型在链路里的位置"。
- 双角色是线上功能，不是本地替身。

代价：每一步真实模型调用都会产生费用和记账。项目内部次数上限已取消（`audit_only`，保留记录），但供应商余额/限流/超时仍然存在，**不要为了"再看看结果"连续点"核查所选事件"**。

### 1.2 演示前准备（5 分钟，一次性）

1. 打开入口：`http://47.93.218.52/anlan/console`。
2. **两个独立浏览器上下文**：窗口 A 用普通窗口，窗口 B 用无痕窗口（同一浏览器共用 localStorage 会串身份）。
3. 窗口 A 点"选择演示配置"，选 `.runtime/p12-b5-access/applicant.json`，页头应显示 **申请人（演示身份）**。
4. 窗口 B 同理选 `.runtime/p12-b5-access/safety-manager.json`，页头应显示 **安全人员（演示身份）**。
   - 不想传配置文件时，也可以把令牌直接粘进"测试访问令牌"输入框；令牌只在页面内存里用一次，**不要写进演示脚本、笔记或录屏**。
5. 两端各自点左上角"＋ 新建会话"，本轮不复用旧申请（旧记录不会被删，只是不参与本轮）。
6. 令牌、配置内容**不要出现在录屏和截图里**。
7. 页面顶部横幅会写 `DeepSeek · deepseek-flash · SYNTHETIC · 不提供作业批准 · 项目调用次数不限（保留记录）`——这就是本轮定位，开场可直接念它。

**自检（PowerShell，10 秒，不打印令牌）**

```powershell
Set-Location 'D:\src\agent学习\安澜2.0'
foreach ($role in 'applicant','safety-manager') {
  $t = (Get-Content ".runtime\p12-b5-access\$role.json" -Raw | ConvertFrom-Json).tokens[0].token
  $i = Invoke-RestMethod -Uri 'http://47.93.218.52/anlan/console/api/info' `
        -Headers @{Authorization="Bearer $t"} -TimeoutSec 20
  "$role => 角色=$($i.collaboration_role) 模型=$($i.model_mode) 记账=$($i.budget.status) 可核查事件=$($i.capabilities.run_event_review)"
}
```

预期两行分别是 `角色=applicant … 可核查事件=False` 和 `角色=safety_manager … 可核查事件=True`。若第 1 行不通，先解决网络/地址，不要开始演示。

### 1.3 开场话术（30 秒）

> 这里演示安澜把申请人、安全人员和核查依据连起来的过程。两个人各用各的窗口、各用自己的身份，共享同一份申请。全程是合成的学习数据，终点是"材料核查完成"，**不是审批通过，也不是开工授权**。后面出现的报警同样是合成的，安澜不会去控制或关闭真实报警。

### 第一幕 作业前：一句话 → 确认 → 补充 → 人工核查

#### 步骤 1　申请人用一句话说清"对象、方式、位置"

窗口 A 发送（可直接复制）：

> 我要申请动火作业：在合成园区检修区东侧2号工位的中心工作台，对演示试件A的焊缝采用电弧焊补焊；附件说明为试件A位置示意图和焊缝照片说明，本轮全部为 SYNTHETIC 合成演示。

观察：先出现一张 **"请确认安澜的理解"** 卡片，列出 作业位置 / 作业对象 / 作业方式 / 附件说明 四项。

讲：

> 模型只负责"把你的话读成四个字段"，它不建任务。这句话里对象、方式、位置、附件都写清了，所以四项能一次抽全；写糊了它就追问，不会替你猜。

坑：**看到卡片 ≠ 已创建申请**。第一次演示务必停一下再点确认。

#### 步骤 2　确认，建立材料

操作：核对四项 → 点卡片上的 **"确认申请"**。

观察：右侧"当前任务"出现，给出申请编号（记为**申请 X**）、材料 v1、分析状态。材料仍是草稿。

讲：

> 确认之后系统才建这份申请并做一次材料分析；分析完仍然只是草稿，要由申请人自己交给安全人员。

> ⚠️ "附件说明"目前是**文本字段**。本轮没有真的上传照片，不要说成"安澜看过焊缝照片"。

#### 步骤 3　申请人主动提交给安全人员

操作：右侧"提交给安全人员"下拉框选 `safety-manager-demo` → 点 **"提交给安全人员（先确认）"** → 卡片列出 申请 X / 材料版本 / 核查人 → 点 **"确认"**。

观察：左侧"我的申请"里申请 X 状态变为 **待安全人员核查**。

讲：

> 准备材料、和把它交给对方核对，是两个动作；重要动作都要本人二次确认。这也是"人工留痕"的最低要求。

#### 步骤 4　安全人员在自己的会话里看到同一份申请

操作：窗口 B 点左侧 **"分配给我的待办"** 里的申请 X（必要时点"刷新"，页面每 3 秒轮询一次）。

检查三点：① 两端申请编号相同；② 安全人员能看到共享材料与共享时间线；③ 安全人员**看不到**申请人的私人聊天。

讲：

> 双方共享的是"材料和业务进展"，不是聊天记录。身份来自服务端可信配置，不是页面上选的。

#### 步骤 5　安全人员提出具体补充要求

操作：窗口 B 右侧"提出补充要求"文本框（**一行一条**）：

> 请把作业位置补充到检修区东侧2号工位，并写明演示试件A的摆放点。

→ 点 **"提出补充要求（先确认）"** → 核对卡片 → **"确认"**。

观察：申请 X 变为 **待申请人补充**；窗口 A 的会话里出现同一条要求（来自共享业务时间线）。

讲：

> 这条意见是人提出的，不是模型发现的问题。模型的角色是把材料和依据整理给你看，不替安全人员下判断。

#### 步骤 6　申请人在原申请里补充并重提

操作（窗口 A）：

1. 确认仍在**申请 X**（不要点"发起另一项"）；
2. 聊天框发送：

> 补充作业位置：合成园区检修区东侧2号工位，演示试件A摆放在该工位中心工作台上；其余字段不变，全部为合成演示。

3. 右侧材料版本递增（v1 → v2），旧版本仍保留；
4. 在"重新提交申请"说明框填写：

> 已补充东侧2号工位和试件摆放点，请核对本轮最新材料。

5. 点 **"重新提交申请（先确认）"** → **"确认"**。

讲：

> 补材料、重新提交还是两个动作。版本号递增而不是覆盖，所以后面复盘时能看到"改了什么"。

#### 步骤 7　安全人员完成人工材料核查

操作（窗口 B）：刷新 → 核对最新版本 → 在"完成人工材料核查"说明框填写：

> 已人工核对本轮位置、对象、方式和附件说明，材料核查完成。本记录仅表示材料核对，不代表作业正式批准或开工授权。

→ 点 **"完成人工材料核查（先确认）"** → **"确认"**。

观察：双方都显示 **材料核查完成**，共享时间线保留 提交 → 补充要求 → 重提 → 完成 四条记录；完成记录绑定在**第二版材料**上。

**第一幕收尾必说的一段**

> 现在这个状态叫"材料核查完成"，它不等于作业批准。安澜不做正式审批、不发开工许可、不销票。真实作业起始时间、人员到场、区域准入，都不在这个系统里。

### 第二幕 作业中：事件到达 → 依据 → 受限候选 → 人工反馈

> ⚠️ 这一幕有一个必须当场讲清的落差：**安澜没有接入视频平台和气体平台，也没有订阅/消费链路。**"＋ 未戴安全帽 / ＋ 气体浓度异常"两个按钮是在页面里生成一条**合成事件**，冒充"平台送来一条告警"。按钮之外没有摄像头推理、没有传感器采样。

#### 步骤 8　模拟一条"未戴安全帽"事件

操作（窗口 B，保持申请 X）：展开右侧 **"事件、核查与反馈详情"** → 点 **"＋ 未戴安全帽"**。

停顿，然后说：

> 这一步只是"平台送来一条事件"，还没有查任何东西。原始报警状态是 `active`，安澜不关警、不压制。

#### 步骤 9　发起核查（真正调用工具的那一步）

操作：在事件列表里**选中刚生成的这条** → 点 **"核查所选事件"**（等 5—20 秒）。

观察（页面会显示）：核查状态、关注项（如 `helmet_missing` / `context_for_review`）、三行依据 `依据：query_worker_qualification · ok` 之类。

讲（这段是第二幕的核心）：

> 点上"核查所选事件"这一刻，才真正发起三条**只读查询**：查这名作业人员的资质记录、查这个区域的状态、检索已入库的规程知识；然后由模型在这些结果上生成**受约束的候选关注项**。
>
> `ok` 只表示"这次查询拿到了符合合同的结果"，**不代表作业安全**，更不是审批通过。查不到就如实留成缺口，不会现场编造证书或制度。

这三条依据的真实取值（2026-10-25 云端实测，见 `docs/phases/phase-12-dual-role/evidence/batch-05/live-event-review.json`）：

| 编号 | 工具 | 实测结果 | 怎么讲 |
|---|---|---|---|
| o1 | `query_worker_qualification` | `ok`，`status=active`，`welding` | 合成人员资质有效，但这只是记录有效 |
| o2 | `query_area_status` | `ok`，但 `status=restricted` | **查询成功 ≠ 状态正常**：该合成区域是受限状态，要交给人工处置 |
| o3 | `query_knowledge` | `ok`，命中 3 条合成制度引用（准备 / 条件变更 / 气体事件），带有效期 2026-01-01 → 2027-01-01 | 引用是"待人工核对适用性"的候选，不是自动结论 |

> 讲 o2 时不要含糊：这里恰好是"工具成功、业务异常"的典型例子，是全场最值钱的一句话。

#### 步骤 10　记录人工反馈

操作：下方"安全管理人员反馈"下拉框选 **需要继续核实** → 点 **"保存人工反馈"**。

观察：反馈已保存；**原始报警仍是 `active`**。

讲：

> 反馈只记录人的意见，不改报警、不产生处置工单、也不等于"风险已解除"。三个选项分别是 需要继续核实 / 确认事件 / 对事件有异议——"确认事件"也只是确认"这条事件存在"，不是确认风险消除。

#### 步骤 11　第二条：可燃气体浓度异常

操作：点 **"＋ 气体浓度异常"** → 选中新事件 → **"核查所选事件"** → 单独保存本条反馈（不要复用上一条）。

观察：事件类型 `gas_abnormal`，同样走三条依据，同样生成受限候选。

讲（对齐你的原设想）：

> 你设想的"监听并消费两条告警"，在这里是**手动注入的两条合成事件**；真实的订阅消费、自动派单、IM/短信推送都还没有。安澜现在能证明的是：**事件到达之后，它怎么把依据查出来、怎么把不确定性留给人工**。

#### 第二幕可选加演（会多消耗一次模型调用，第一次演练可跳过）

演示"旧结论不能冒充最新结论"：换一份新申请 → 在待核查阶段先做一条事件核查 → 安全人员要求补充位置 → 申请人改材料重提 → 回到旧核查，状态变为 **材料已变化 / `stale_material`**（只读保留，原始报警与人工反馈都不丢）。

### 第三幕 作业后：回看 → 归因 → 沉淀（本幕是"设计出来"的，前两幕是"演出来"的）

> 你说作业后不太了解——现状确实**没有一键生成"作业复盘报告"的功能**，也没有完工验收与销票。所以这一幕的门票是：**记录已经存在，复盘由人做，模板由你带。**下面这套三步法都能用现有页面与本地命令完成，不需要改代码。

#### 第 1 步　回看：把事实从页面读出来（3—5 分钟）

操作（窗口 B，申请 X）：

1. 展开 **"共享业务时间线"**：逐条读出 提交 / 补充要求 / 重新提交 / 材料核查完成，记下时间和操作人。
2. 展开 **"事件、核查与反馈详情"**：分别点两条事件，逐条记下：事件类型、原始报警状态、核查"当前有效"还是"材料已变化"、三行依据的结果。
3. 回到窗口 A 刷新：确认双方看到同一进展（同一申请编号、同一状态）。

讲：

> 复盘的第一性原则是**只记录系统里确实存在的证据**。这里能证明的是：材料怎么补齐的、谁在什么时候提了什么要求、事件何时到达、当时查到了什么依据、人工留下了什么意见。这里**证明不了**：现场是否真的安全、作业是否真的完成、报警是否真的解除。

#### 第 2 步　归因：用"三类缺口"给每个问题定位（2—3 分钟）

这是作业后最值得教给别人的分析框架，也是安澜产品说明里明确的三分法：

| 缺口类型 | 判断依据（看哪里） | 谁该做下一步 | 反例（不许做的事） |
|---|---|---|---|
| **材料没说清** | 时间线里出现过"待申请人补充"；材料版本从 v1 升到 v2 | 申请人补材料，再重提 | 不许让模型"猜一个位置"填进去 |
| **系统有、但这次没查/没取到** | 依据行是 `unknown` / `error`，或核查被标记"材料已变化" | 安全人员显式重查（换材料版本后旧结论失效） | 不许拿旧核查当最新结论 |
| **源系统真的没有** | 依据 `unknown` 且原因是"无可用证据" | 数据维护方补源数据 / 补知识库；不是申请人能解决 | **绝对不许让模型编造证书、制度、区域状态** |

再补一条**模型层面**的归因：

> 候选关注项是"辅助线索"，不是结论。模型漏了什么、多了什么，要人工标出来；这也正是下一条"沉淀"要用的原料。

#### 第 3 步　沉淀：一页复盘卡（人手填写，模板即交付物）

> 目前"给反馈"**不会**自动变成 Badcase，也**不会**自动更新模型或知识库。所以这一步的产物是一张人写的卡，由你复制进笔记/工单：

```text

材料：首版 v__ → 终版 v__；是否经历"补充要求→重提"：__
材料核查：核查人____；本轮人工说明：____
事件：未戴安全帽__条 / 气体异常__条（按本轮实际生成数）
核查：完成__条；失败/取消__条；已过时__条
依据：资质__（ok/unknown/error）；区域__（正常/受限/未知）；知识引用__条
人工反馈：需要继续核实__；确认事件__；对事件有异议__
三类缺口归属：材料__ / 未取到__ / 源系统没有__
未解决事项：____________
外部处置：有独立记录则引用；没有就写"本系统未记录/未验证"
改进建议：如"首次申请就写到具体工位"、"受限区域规则进知识库"、"某类事件补一条评测样例"
边界声明：材料核查完成 ≠ 作业批准；人工反馈 ≠ 报警关闭；本卡由人填写
```

#### 第 4 步（可选，加分）沉淀到"可靠性回归"：离线质量回放

这是"作业后闭环"里**唯一能跑起来、且零模型调用**的工程化环节。在项目根目录：

```powershell
Set-Location 'D:\src\agent学习\安澜2.0'
$env:PYTHONUTF8 = '1'
# 只看冻结评测集的元数据，不重新验证、不调模型
.venv/Scripts/python.exe -m anlan.interfaces.quality_cli inspect --manifest evals/quality-v1/manifest.json --output .runtime/post-work-inspect-01.json
# 只对已记录的候选重跑当前验证器：不重跑工具、不调模型
.venv/Scripts/python.exe -m anlan.interfaces.quality_cli replay --manifest evals/quality-v1/manifest.json --split dev --output .runtime/post-work-replay-dev-01.json
.venv/Scripts/python.exe -m anlan.interfaces.quality_cli replay --manifest evals/quality-v1/manifest.json --split holdout --output .runtime/post-work-replay-holdout-01.json
```

本轮实测输出（2026-10-28）：

```text
inspect  : status=completed  model_requests=0
replay dev: matches_expected=6  not_replayable=2  model_requests=0
replay holdout: matches_expected=5  not_replayable=0  model_requests=0
```

讲：

> 这是"冻结评测集 + 离线回放"。它的用途是：当你改了提示词、校验器或工具合同之后，能立刻看出有没有把历史案例弄坏。注意两点：① `not_replayable=2` 要如实说——旧记录缺输出，只能看状态，不能补录成"成功"；② 这条链路**不会**把刚才那份申请自动变成新用例，把本次问题写成 Badcase 仍然是人工动作。

#### 第三幕收尾话术（20 秒）

> 作业后的正确说法是：**"我们完成了可追溯的复盘"**，而不是"系统生成了复盘报告"。记录是系统留的，判断是人做的。这套东西真正积累下来的资产是：一致的材料字段、可复核的依据、可回放的历史案例。

## 2. 本地零成本路线（没有云环境时用这条，5—10 分钟）

完全离线、零模型调用、不需要数据库和网页。适合课堂热身，或者"先看控制流再上云端"。

```powershell
Set-Location 'D:\src\agent学习\安澜2.0'
$env:PYTHONUTF8 = '1'
uv sync --locked --link-mode copy     # 首次
uv run anlan demo                     # 打印三行 JSON 快照
uv run anlan chat                     # 交互式补充材料；/quit 退出
```

本轮实测 `anlan demo` 的三行状态：revision 1（缺位置、方式，`waiting_input`）→ revision 2（只缺方式）→ revision 3（`awaiting_review`），task/correlation 不变、run 每次变。`chat` 里逐次补充这两个局部字段即可：

```json
{"work_location_description":"SYNTHETIC：演示 A 区 1 号台"}
{"work_method_description":"SYNTHETIC：电弧焊连接接缝"}
```

讲：

> 这是"材料追问 → 局部补充 → 再分析"的最小闭环，规则模式，`semantic_status=offline_not_checked`。它能讲清"任务状态怎么按版本往前走"，**不能**用来证明模型读懂了你的话。

## 3. 未满足项：怎么处理，而不是假装有

### 3.1 "审核期间发现资质/位置/规程知识库缺少 → 触发 Agent 调工具补充"

这是你设想里最重要、也最容易讲错的一条。真实情况分四层，建议按这个顺序讲：

1. **能力存在**：三条只读工具都已实现并可实际执行——人员资质、区域状态、规程知识检索（本地合成数据、租户/读者/有效期/撤回都受约束）。
2. **云端触发点在"事件核查"**，不在"审批前"。第一幕里你点不出"自动查资质"；要在第二幕点"核查所选事件"才看得到三条依据。（我本次拉取线上 `app.js` 核对过：线上页面**没有**"作业前依据"卡片相关代码。）
3. **作业前自动预核查（P13）**：设计已确认、服务层已实现并验收（B1/B2），**页面（B3）仍在实施、未验收、未部署**。当前工作树里它已经能跑通一半，但本机跑相关测试是红的——三个预核查测试文件里有 4 项失败，全量跑时未提交的 P13 用例共 14 项失败（另有 3 个 P12 协作用例也红，同样属于未提交改动范围）。代表性的 4 项：

   ```text
   tests/test_preflight_conversation.py::test_human_citation_candidate_freezes_real_ids_and_rejects_stale_card
   tests/test_preflight_conversation.py::test_human_citation_choice_rejects_check_replaced_before_card_creation
   tests/test_preflight_gate.py::test_completion_rejects_missing_frozen_fields_and_arbitrary_references[duplicate]
   tests/test_preflight_gate.py::test_legacy_unbound_submission_requires_supplement_and_can_resubmit_same_material
   ```

   所以**不要把它当演示卖点**；当成"下一步"讲。
4. **顺序和你想的不一样（这点必须说清）**：实现是"**提交/重提就自动查三项**"，不是"模型先发现资料缺，再决定调哪个工具去补"。缺数据时的行为是：留缺口（`gap`）、阻断"完成人工材料核查"、允许修源数据后显式重查；**绝不由模型补造**证书、制度或假设合格。

   本轮我在本机实跑过这条链路（服务层行为）：提交后自动产生预核查，结果为 `status=gap`、`issues=["knowledge_citations_missing"]`（资质 `active` 正常、知识检索 `unknown no_eligible_evidence`）——因为本地知识库是空的。这正是"知识库不足"的真实形态：**它不会补出制度，它把缺口留给你。**

**现在能说的三句话 / 不能说的三句话**

| ✅ 可以说 | ❌ 不能说 |
|---|---|
| "资质、区域、规程三条依据都能查，并在事件核查里实际执行" | "系统在审批前自动补齐了缺失资料" |
| "依据不足时保留 `unknown` 并阻断完成，交人工处置" | "Agent 自己发现知识库缺什么就去补了什么" |
| "作业前自动预核查是正在开发的下一个版本（P13），页面尚未验收" | "线上已经在用作业前预核查" |

### 3.2 "监听消费视频告警 + 气体异常"

- 现状：两个页面按钮 = 两条合成事件；没有 Kafka/MQ/HTTP 回调等任何消费端（全仓库检索无订阅/消费实现），没有摄像头、没有传感器采样。
- 可以说："事件进入系统之后的处理链路已经打通，事件来源当前是模拟注入。"
- 不能说："安澜在监听视频流"、"安澜识别到了某个人没戴安全帽"、"阈值是现场真实阈值"。

### 3.3 "自动推送安全人员"

- 现状：安全人员页面每 3 秒轮询自己的待办/收件箱；提交、补充要求、重提、完成会产生协作通知。**事件核查不会自动派单**，也不会触发短信/IM。
- 可以说："安全人员能在他自己的待办里看到分配给他的申请和协作通知。"
- 不能说："报警一发生，安澜就自动研判并推送给安全人员了。"

### 3.4 "作业后自动总结"

- 现状：没有自动报告、没有完工/销票、反馈不自动进 Badcase。有：版本化材料与业务时间线、事件与依据、人工反馈、过时标记、冻结评测集 + 离线回放。
- 可以说："我们现在做的是**可追溯的人工复盘**。"
- 不能说："系统生成了本次作业的复盘报告/改进建议"。

## 5. 常见卡点与先查什么

| 现象 | 先查什么 |
|---|---|
| 安全人员看不到申请 | 申请人是否**点过确认**（提交是两段式）；核查人是否选对；两端是否同租户；是否点了"刷新" |
| 输入"确认"却没变化 | 页面上是否真有待确认卡片；是否有红字报错；右侧状态是否变了。**不要连点、不要另建申请** |
| "消息已保存，但本次处理失败" | 历史失败不会被删除；先刷新核对状态再决定是否重试，避免重复消费模型调用 |
| 有事件但没有核查结果 | 生成事件 ≠ 核查；是否点了"核查所选事件"；是否选中了那条事件 |
| 依据 `unknown` / `error` | 如实讲缺口，不说"核查通过"，不现场补造 |
| 页面看不到完整建议或引用原文 | 现在的 UI 只渲染部分结果；想看得更细按 F12 → Network → 该次核查的 `GET /reviews/{id}` → 看 `result.report`（不要导出 Authorization） |
| 反馈看起来不对 | 是否选中了正确事件对应的核查（两条事件容易串） |
| 报警仍是 `active` | 正常边界：安澜没有关警能力 |
| 想演"旧核查过时" | 必须用**另一份新申请**，已完成材料会被冻结、不能再改 |
